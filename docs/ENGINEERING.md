## 0. 结论先行

**这是一份工程质量中上、架构清晰的项目，不是一份需要推倒重来的代码。**

真正的问题不是"代码写得烂"，而是**质量投入的分布与业务风险完全错配**：

> 系统 90% 的产品价值来自 RAG 检索链，但检索链是全项目测试覆盖最低、类型检查最松、函数粒度最大的部分。

因此本报告的核心结论是：**不要全面重构，而是把工程资源从"已经很稳的地方"搬到"风险最高但最薄弱的地方"。**

> **⚠️ 门禁容差比实测噪声还窄（后续轮次实测，需要关注）**
>
> 连续跑 7 次 `retrieval_gate`，**6 次完全相同**（`hit@1`=0.9000、`MRR`=0.9458、
> `precision`=0.9000、`evidence`=5.2500），**1 次明显偏高**
> （0.9250 / 0.9583 / 0.9139）。
>
> **离群幅度 +0.025 > `_METRIC_SPECS` 的容差 0.02** —— 也就是说
> **如果那次漂移是负向的，门禁会报一次假回归**。
>
> 为什么会有这种离群：门禁**每次都重建全新索引**，而 HNSW 图构建是多线程的、
> 本身带不确定性。所以噪声来源不只是查询期的 ANN 近似，**还有建索引期**。
>
> **建议**（未做，属 CI 策略）：把容差放宽到 0.03，或让门禁跑 3 次取中位数 ——
> 否则值班的人会遇到"什么都没改却红了"。

> **★★ 后续实测推翻了上面这条的优先级：更大的问题不是「容差窄」，而是「索引故障被当成质量退化」。**
>
> 为验证「单线程建图能否消除噪声」，连跑两次完整建索引，结果第一次 `hit@1` 只有 **0.725**
> （正常 0.95）—— 波动 **0.225**，是容差（0.02）的 **11 倍**、是上面那条噪声（0.025）的 **9 倍**。
>
> **根因不是噪声**：`data_structure` / `computer_organization` 报
> 「Error creating hnsw segment reader: Nothing found on disk」——
> **建索引期的就绪检查通过了，检索期才失败**。而检索链对单路失败是**静默降级**
> （`asimilarity_search_with_score` 返回 `[]`），于是门禁把这种**无意义的指标**
> 当成正常指标去比对基线：**既可能报出巨大的假回归，也可能掩盖真实退化。**
> 相比之下「容差 0.02 偏窄」只是小问题。
>
> **✅ 已修（三道）**：
> 1. `VectorStoreManager.query_failures` —— 查询失败的**可观测出口**（异步查询失败时记录集合与异常类型）
> 2. 门禁在**比对基线之前**断言它为空；非空则打印原因并**以退出码 2 结束** ——
>    「明确说不知道」优于「报一个假结论」
> 3. ★ **只统计「本次真正建过索引」的集合**：检索链会查询 `answers` 等**可选集合**，
>    它们不在 `DEFAULT_CATEGORIES` 里、本来就不存在，查询失败是**设计内的降级**。
>    判据用 `built` 集合过滤，**不匹配错误文案**（后者依赖 Chroma 措辞，升级即失效）
>
> **反向验证 2/2**：去掉记录语句 → 1 条变红；去掉过滤 → 3 条变红。
> ★ **修复的第一版不过滤，被 `answers` 误触发** —— 结果是**正常运行时也报「指标不可信」**，
> 实跑一次才发现并改正。这是「改完必须实跑，不能只靠读代码」的又一例证。
>
> **关于「容差 / 中位数」**：本条修复后，那 0.025 的离群仍是**独立的小问题**，
> 但优先级低于上面这条。放宽容差或跑 3 次取中位数**尚未做**，留作后续。

> 却挤掉了更好的证据。
>
> **结论：短 section 被丢弃是**调优过的设计**，不是遗漏。**
> "找回内容"≠"提升质量"：这些碎片对检索是**负价值**。
>
> **★ 这条与 #13 合起来给出一个更强的结论**：
> **`splitter` 的粒度参数（`MIN_CHUNK_LENGTH` / `_ADAPTIVE_CHUNK_SIZE` / 标题层级）
> 是一个互相咬合的整体，且已经过调优。** 单独动任何一处（放宽标题层级、或保留短 section）
> 都会让指标一致下降。要改进必须**整体重调并重校基线**，而那是另一个量级的工作。

**风险**（为什么这是 P0，而不是"慢慢补"）：

1. **改动无法验证**。`retriever.py` 里有 `SCORE_THRESHOLD = 0.06`、`_RERANK_EXPAND_FACTOR = 5`、按查询类型 1.2/0.75/1.1 的阈值微调、按类型 5/6 的候选池倍率——注释写着"基于采样校准"。**今天没有任何自动化手段能证明改动这些常数不会让检索质量退化**。每次调参都是盲调 + 人工抽查。
2. **重构失去安全网**。想拆那个 447 行的函数，但没有测试证明"拆完行为不变"，于是没人敢动。技术债由此固化。
3. **失败模式被掩盖**。检索出问题时的表现是"答得不对"，而这条链上任何一环静默降级（rerank 超时、缓存污染、路由全部 miss）都只是"答得不对"，无法定位。
4. **`codecov.yml` 只排除了 `src/tools/`**，导致 36% 的总覆盖率**看起来只是"中等"**，掩盖了风险高度集中这一事实。指标失去了指导意义。

**改进方案（可落地，分三步）**：

  > 全部经反向验证（注入 9 类真实缺陷 → 断言全部变红 → 恢复后回绿）。
  > 实测 `retriever.py` 覆盖率 **7% → 18%**，`recall.py` 16% → 20%，全量 555 passed。

  > **注意：实测值 18% 低于本节原先预估的「30%+」，这个差距本身是最重要的信息。**
  > `retriever.py` 的 747 条语句里，绝大多数位于两个 400+ 行的流水线函数中，而它们必须
  > 跑完整链路（依赖 TEI / ChromaDB / LLM）才可能被执行 —— 纯函数测试能触达的语句有**结构性上限**。

### P1 — `splitter` 的 Q&A 原子机制在真实语料上从未激活（死代码 + 死检索路由）

**背景**：补 `splitter.py` 测试时，顺手用真实知识库做了端到端实测，结果发现文档承诺的
「Q&A 对合并为原子单元、不可拆分」这条核心特性，**在 40 个真实知识文件上一次都没生效**。

**实测基线**（`split_documents` 跑全库 `knowledge/**/*.md`，共 40 个文件）：

| 指标 | 实测值 |
|---|---|
| 输入字符 / 产出 chunk | 755,509 / 2,217 |
| 输出字符 / 字符留存率 | 731,740 / **96.9%** |
| 平均 chunk 长度 | 330 字符 |
| `merged_qa` 角色 chunk 数 | **0** |
| `content_type` 实际取值集合 | 仅 `{code_mixed, section}` |

**根因**：`_ANSWER_RE = (?:解答|答案|正确答案)[：:；;]` 与真实语料的标注方式不匹配。

| 真实语料中的标注 | 出现次数 | 是否被 `_ANSWER_RE` 识别 |
|---|---|---|
| `**解析**：` | 240 | ❌ |
| `✅`（标在正确选项行尾） | 251 | ❌ |
| `答案：` | 66 | ✅ |
| `解答：` | 26 | ✅ |
| `正确答案：` | **0** | ✅（但从不出现） |

408 真题用的是「选项行尾打 `✅` + `**解析**：`」，所以 `has_answer_marker` 恒为 False →
`content_type` 永远不会被提升为 `merged_qa` → `_extract_qa_fields` / `_split_qa_oversized` /
`qa.*` 元数据 / `section.chunk_role="merged_qa"` **整条链路从未执行过**。

**连带死代码（跨 4 个模块，这是最值得警惕的部分）**：

| 位置 | 内容 | 实际状态 |
|---|---|---|
| `recall.py:216-231` | `merged_qa_meta` 专用召回路由（按 `content_type="merged_qa"` 过滤） | **恒返回空** |
| `recall.py:283-285` | RRF 权重 `(merged_qa_meta, exercise/answer/comparison)=2.0/2.0/1.5` | 永不生效 |
| `_metadata_spec.py:67-70` | `qa.question` / `qa.answer` / `qa.answer_key` 元数据契约 | 契约有、索引里没有 |
| `rag_utils.detect_content_type:163-166` | `merged_qa` 分支 | 永不触发 |
| `splitter.py` | `_merge_qa_blockquotes` / `_extract_qa_fields` / `_split_qa_oversized` | 约 300 行未被执行 |

**为什么比"功能缺失"更危险**：这是**声明与实现不一致**。下游若按 `qa.answer_key` 取值，
拿到的永远是空串；`recall` 那条路由会白白消耗一次向量检索配额并恒空返回。
关键在于 —— **没有任何日志或指标会提示它没生效**。同一类病在 §1 P2「配置存在但不生效」
已经出现过一次，这次是它的"数据契约版"。

**修复方向（需产品决策，不建议直接改）**：

1. **对齐标注**：扩展 `_ANSWER_RE` 使其识别 `✅` 与 `**解析**：`；或反向统一知识库格式
   （后者要改 6 个真题文件共 278 处）。
2. **先修 `_merge_qa_blockquotes` 的结构性缺陷**（见下表 #2/#3），否则对齐了标注也仍然拆不开。
3. **决定 `merged_qa` 路由的去留**：要么让它有数据，要么删掉路由与权重，别让它"看起来能用"。

> ⚠️ 改动会改变 chunk 切分结果 → 必须重新入库 → 检索质量可能变化。
> **应先用 P0 第二步的「黄金集回归测试」兜底，再动手。**

**本轮用测试钉住的具体缺陷**（每条都在 `tests/rag/test_splitter.py::TestKnownDefects`
留了变更哨兵：断言的是现状，修复后必然变红并迫使同步更新契约）：

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | `split_documents(docs, chunk_size, chunk_overlap)` 的**两个参数在函数体内从未被引用** | 调用方任何调参都静默失效；实际尺寸只由 `_ADAPTIVE_CHUNK_SIZE` 决定 |
| 2 | `_merge_qa_blockquotes` 的输出与 `_parse_semantic_units` 的空行切分**不兼容** | `__QA_PAIR_START__` 只贴在首行，块内空行使原子 Q&A 被 `re.split(r"\n{2,}")` 切碎，答案与题干分离 |
| 3 | 例题模式遇到「答案前的空行」即提前关闭 | 这正是 markdown 常态写法，等于该模式基本不可用 |
| 4 | 短例题 section **产出 0 个 chunk** | 内容静默丢失、不进索引（合成用例：`## 例题精讲` + 短例题 → 0 chunk）。**真实语料上影响很小**，见下方「真实留存率实测」 |
| 5 | 原子单元（表格/公式）会被 `_merge_short_chunks` **合并回邻居** | ⚠️ **经门禁实测后判定为「有意为之，不是缺陷」**，详见下方「一次被门禁拦下的错误修复」 |
| 6 | `_split_oversized` 注释声称有「单句超 limit 的兜底」，**实际不存在** | ✅ **已修**：500 字符单句在 limit=100 下仍产出 1 个 500 字符 chunk（现按 limit 硬切，反向验证 3/3） |
| 7 | `_extract_headings` 只认 `#{1,4}` | 真实库中 **80 处** `##### 1)内容` 五级标题完全不可见，section 层级与 `heading_path` 失真 |
| 8 | `_add_prose_unit` 的 1200 上限**未计入拼接空格** | 实测产出可达 1319 字符，超出自设上限 |
| 9 | 代码块占位符自带换行（`\n__CODE_BLOCK_n__\n`） | 在 Q&A 块内制造空行，同样触发切碎 |
| 10 | `content_type in ("exercise","answer")` 是**死条件** | 调用 `detect_content_type` 时未传 `source_ext`，这两个分支永不命中 |

### P1 — 宽泛异常处理吞噬错误，调试成本高

**证据**：全项目 **92 处 `except Exception`**，其中 **13 处 `except: pass`**（`semantic_cache.py:154/215/524/607`、`loader.py:43/67`、`parse_utils.py:57/65/73`、`evidence.py:80`、`imputer.py:721`、`ragas_eval.py:100/108`）。

**典型模式**：

```python
except Exception as e:
    logger.error("Retrieval failed: %s", e, exc_info=True)
    return RetrievalResult(status="error", context=f"检索失败：{e}", ...)
```

**为什么是问题**：

- 调用方拿到的是**字符串化的错误**，无法区分"知识库确实没有"（`status=empty`）、"外部服务挂了"（TEI 超时）、"代码写错了"（`KeyError`）。**这三者需要完全不同的处置，现在被抹平成同一类**。
- `except: pass` 更严重：`semantic_cache.py` 静默吞掉异常意味着"缓存坏了但你以为在缓存"，性能与成本问题会长期潜伏。
- 92 处 catch-all 意味着**日志里出现 ERROR 时，你无法判断严重程度**——真实故障被淹没在噪声里。

**改进方案（分层错误策略，见 §2 规范）**：

1. **定义异常层级**，替代字符串化错误：
   ```python
   class RagError(Exception): ...              # 检索域基类
   class RetrievalUnavailable(RagError): ...   # 外部依赖不可用 → 可降级/可重试
   class RetrievalEmpty(RagError): ...         # 正常空结果 → 不是错误，不记 ERROR
   class RagInternalError(RagError): ...       # 代码缺陷 → 必须告警
   ```
2. **禁止 `except: pass`**：确需忽略时，必须 `logger.debug(..., exc_info=True)` 并写注释说明为何安全。
3. **catch-all 只允许出现在"最外层边界"**（HTTP 路由、agent 工具入口），且必须区分 `except (RetrievalUnavailable, TimeoutError)` 与 `except Exception` 两级，后者一律 `logger.exception` + 上报。
4. **空结果不是错误**：`status=empty` 走正常返回路径，不产生 ERROR 日志。

> **✅ 第一步已落地（后续轮次）** —— 但**刻意只做了一半**，理由如下。
>
> **已做**：
>

> |---|---|
> | 异常层级 `RagError` / `RetrievalUnavailable` / `RagInternalError` | 新增 `src/rag/errors.py`（**100% 覆盖**，14/14 语句） |
> | 分类器 `classify_retrieval_error()` | 同上（网络/超时 → Unavailable；其余 → Internal） |
> | **调用点抛正确类型**：TEI HTTP 失败 → `RetrievalUnavailable`；返回 NaN → `RagInternalError` | `src/rag/embeddings.py`（4 处，同步+异步各 2） |
> | **边界分级**：Unavailable → `logger.warning` + 可重试文案；其余 → `logger.exception` | `src/agents/tools.py::_retrieval_error_payload` |
> | 机器可读分类 `error_kind` | `src/schema/evidence.py` |
>
> **★ 一处有意偏离设计稿：不实现 `RetrievalEmpty`。** 空结果在本项目走的是**正常返回路径**

> 「正常」与「故障」共用同一条控制流 —— 那正是这一项要消除的问题。

> **★ 为什么只做一半（而不是改完 94 处 catch-all）**：

>    而全项目只有 `agents/tools.py` 构造 `RetrievalResult`（已核实：3 处构造点全在该文件）。

> 2. **分类的可靠性取决于调用点**，不取决于边界。`embeddings.py` 原先把 HTTP 失败和
>    NaN 都抛成通用 `RuntimeError` —— 边界**不可能**区分它们。所以先把最容易出错的那条

### P1 — 检索结果不可复现：RRF 并列排序依赖线程完成顺序

**证据**（本轮建立质量门禁时暴露）：同一份代码、同一份索引、同一条 query，连续 4 次运行
门禁，指标在噪声区间内抖动：

| 运行 | `category_hit@1` | `category_precision` | `mean_evidence_count` |
|---|---|---|---|
| 1 | **0.9250** | **0.9151** | **5.3000** |
| 3 | 0.9000 | 0.9014 | 5.3250 |
| 4 | 0.9000 | 0.9014 | 5.3250 |

**根因**（`rag/postprocess.py`，两处同款）：

```python
ranked.sort(key=lambda item: item[1], reverse=True)   # merge_route_results / weighted_rrf_merge
```

Python 的 `sort` 是**稳定排序**：只按分数做键时，**分数并列的文档会沿用插入顺序**。
而插入顺序来自 `merged` 字典的写入次序 —— 也就是 `_multi_route_search` 里
`ThreadPoolExecutor` + `as_completed()` 的**线程完成次序**。于是：

> **同一条 query，每次运行返回的证据排列都可能不同。**

**为什么这是 P1，而不是"测试有点抖"**：

1. **产品行为不可复现**：同样的提问，两次可能拿到不同顺序的上下文 → LLM 答案不同。
   用户投诉"同一个问题答案不一样"时，这条链上没有任何日志能解释。
2. **门禁失效**：噪声幅度（`hit@1` 约 0.025）**大于**容差（0.02），
   意味着"1 条 query 的真实退化"与"随机抖动"无法区分 —— 门禁要么漏报、要么误报。
   这是"指标失去指导意义"的又一实例（同 §1 P0 第 4 条）。
3. **偶发 bug 会因此变成"不可复现"**：任何依赖结果顺序的下游逻辑
   （去重、截断、top-k 选择）都会继承这个不确定性。

**修法（已落地）**：给排序加**确定性的次级键**：

```python
ranked.sort(key=lambda item: (-item[1], _dedup_key(item[0])))
```

`_dedup_key` 就是 `merged` 的键，因此唯一且确定，能给出全序。两处排序都已修正。

> **反向验证 4/4**：退回稳定排序、次级键取反、主键方向写反、只改一处 —— 全部被断言抓到。
> 修完后门禁连续 4 次运行指标**逐位一致**。

**这里有一条更普适的教训**：**在拿一个门禁去判定别人之前，先测量门禁自身的噪声。**
本轮如果直接接受"跑三次都一样"的巧合，就会把一个噪声高于容差的门禁当成质量闸门，
后续所有"退化"判定都不可信。

### P1 — 假模型开关不封闭：`USE_FAKE_MODEL=true` 时检索链仍调用真实模型

**这是本轮最严重的发现，因为它同时污染了"测试"和"评测基线"两件事，而且全程不报错。**

**根因（两处叠加）**：

1. **`get_llm()` 没有 fake 分支。** `get_model()`（agent 层）有：
   ```python
   if parse_model_ref(model_ref)[0] is Gateway.FAKE:
       return FakeToolModel(...)
   ```
   而 `get_llm()`（RAG 检索链）直接走 `_cached_client` → 构造真实 `ChatOpenAI`。
2. **`USE_FAKE_MODEL` 不覆盖 `LLM_MODEL`。** `model_post_init` 只在
   `DEFAULT_MODEL` 为空时填假值，而 `LLM_MODEL` 的**默认值本身就是真实模型**
   （`deepseek:deepseek-v4-flash`），`.env` 里通常还显式配了真实引用。
   更糟的是 `_validate_model_ref` 在覆盖之前执行 —— 无 key 环境会在覆盖生效前就先抛错。

**后果分两种环境，都很难察觉**：

| 环境 | 表现 |
|---|---|
| 本地（`.env` 有真实 key） | 检索链**真的调用线上模型**。decompose / HyDE 用温度 0.3 → 每次结果不同、基线不可复现、产生费用。**没有任何报错。** |
| CI（无 key） | `openai.OpenAIError: Missing credentials`。实测 **40 条门禁 query 里 6 条直接崩溃**，异常穿透 `aretrieve_evidence_with_retry` 之外，门禁只留下 traceback。 |

**实测证据**：同一份代码跑门禁，本地（真实模型）与封闭环境（假模型）指标不同 ——

| 指标 | 真实模型（本地） | 假模型（封闭） |
|---|---|---|
| `category_precision` | 0.9014 | **0.9005** |
| `mean_evidence_count` | 5.325 | **5.275** |

**也就是说：此前提交的检索门禁基线，是"跑在真实 LLM 上"录出来的。** CI 用假模型，
数字对不上，门禁在 CI 里要么误报要么靠容差侥幸通过 —— 而我当时把连续 4 次一致
当成了"确定性已修复"的证据。**那是巧合，不是设计。**

**修法（三处，已落地）**：

1. `get_llm()` 补 fake 分支（与 `get_model` 对称，且 `FakeToolModel` 不进缓存 —— 它有状态）。
2. `model_post_init` 在**任何校验之前**把 `DEFAULT_MODEL` 与 `LLM_MODEL` 一起拉回假网关。
   顺序是关键：放在校验之后，无 key 环境会在覆盖生效前就抛错（这条是测试先抓出来的）。
3. `configure_for_gate` 显式设置两个模型引用（**故意的重复**：门禁的正确性不该依赖
   settings 的默认推导），CI job 也显式加 `USE_FAKE_MODEL=true`（否则 settings 构造阶段就失败）。
4. `run_gate` 改为**单条 query 抛异常不中断整轮**：记成"空结果 + 错误原因"，
   门禁照样给出完整指标并单独列出错误；`--update-baseline` 遇到异常直接拒绝录基线
   （否则会把故障固化成基准）。

**顺带修掉的同类问题**：`_validate_model_ref` 与假值覆盖的顺序（见上）。

**新增 15 条测试**（`tests/core/test_fake_model_hermeticity.py`）：断言落在
"拿到的客户端类型"和"模型引用"上，而不是"没抛错" —— 这类缺陷的共性是**默认路径看起来是好的**。

> **教训（已写进 §3.1-G）**：**"没报错"不等于"环境是封闭的"。**
> 评测类改动的验收标准必须包含"它依赖哪些外部资源"，并在**无外部资源的条件下**跑一遍。
> 本轮如果一开始就用"清空凭据"的方式验证门禁，这个缺陷会在第一次就暴露。

### P1 — recall 阶段残余非确定性：已定位到 Chroma ANN 边界（低频、被下游吸收）

**怎么发现的**：为拆分 `aretrieve_documents` 而新建的阶段级追踪器（`evaluation.stage_trace`）
记录每个阶段函数的入参与返回值。它比门禁**敏感得多**：门禁只看最终 top-k 的身份与聚合指标，
而追踪器能看到中间阶段。

**逐层定位（关键方法）**：把召回链按层 dump 签名，找**最低**发生差异的那一层：

| 层 | 内容 | 跨进程一致性 |
|---|---|---|
| L1 | `avgdl`（每个集合的平均文档长度） | **一致** |
| L2 | `bm25_search` 的 top-k | **一致** |
| L3 | `_raw_search` 逐路由的候选 | **不一致** ← 最低差异层 |
| L4 | `_amulti_route_search` 的完整输出 | 一致 |
| L5 | `aretrieve_documents` 的最终文档 | 一致 |

**具体表现**（`computer_organization:semantic`，"栈和队列的主要区别是什么？"）：

```
run1: … ('dbea6aaf', 0.8573), ('50296df0', 0.8609), ('e30b26eb', 0.8610)
run2: … ('84911dc4', 0.8501), ('dbea6aaf', 0.8573), ('50296df0', 0.8609)
       ↑ 距离更优（0.850 < 0.861），但 run1 没返回它
```

**这是近似检索的漏召**：不是"顺序不同"，而是**首次访问时少返回了一个本该进 top-k 的候选**。

> **⚠️ 更正（后续实测推翻了我先前的结论）**：我一度写"该差异被下游融合/去重吸收，
> 产品侧无可观测影响"。**这个结论是错的。** 在做拆分验证时捕获到
> `虚拟内存的作用是什么？` 的 **`最终返回的文档序列变了`** ——
> 即漂移**确实会传导到最终结果**。产品存在低频的"同一问题返回不同证据"，
> 频率约 10 次里 1 次。这对 #28 的影响是：**逐位比对最终结果会周期性误报**，
> 故新增 `probe_query_stability` + `--stable-only`，录基线时先剔除不可复现的 query。

**已排除的原因（全部为实测，不是推测）**：

| 假设 | 实测结论 |
|---|---|
| `decompose` 调真实 LLM 导致子查询漂移 | 成立但**已修**（见上一条 P1）；修完后仍有余量 |
| Chroma HNSW 跨进程重建导致 ANN 不同 | **排除** —— 复用同一持久化索引、且不重建，仍出现 |
| `bm25_search` 的 `avgdl` 采样抖动 | **排除** —— 清缓存连续 5 次重算，取值唯一 |
| `bm25_search` 本身不确定 | **排除** —— 隔离测试 top-k 签名唯一 |
| 原始 `coll.query`（固定向量）不确定 | **排除** —— 进程内 6/6 一致、跨进程 3/3 一致 |
| LangChain `Chroma` 包装器不确定 | **排除** —— 跨进程 3/3 一致 |
| RRF 并列排序依赖线程完成次序 | 已修，**不是**残余原因 |

**⚠️ 未能复现（这一条同样重要）**：初次观测到 run1 离群后（8 次里 1 次），
我用**全新索引**做了受控 A/B —— 不预热 3 次 + 预热 3 次，**6/6 全部一致**。
也就是说：**这是低频、间歇现象，不是系统性缺陷**，我无法稳定复现它。

**结论**：根因在 **Chroma 近似向量检索的 top-k 边界**（上游），不在本项目代码。
本项目的三个可改点（`bm25_search` 的无序截断 / 无序候选集 / 排序无次级键，见 backlog #31）
经隔离测试都是确定的，因此**不是本次现象的原因**，但仍是值得加固的隐患。

**对 #28（拆分 `aretrieve_documents`）的影响与解法**：
不能对 recall 阶段做**逐位严格比对** —— 那样会把上游 ANN 的边界抖动当成重构引入的退化。
正确做法是**分级断言**：

- 阶段调用**序列**与各阶段**入参**：严格一致；
- recall 层**输出**：**只报警、不判失败**（见下）；
- 融合及其之后的所有阶段：严格一致（这部分是我们自己的代码，必须逐位可比）；
- 最终返回：严格一致。

这样既守住了"重构不改行为"的真正契约，又不会因上游近似索引而假报警。

> **✅ 已落地（本轮）**：`evaluation.stage_trace.compare_traces` 实现分级比对，
> 严格模式下 6 次连跑全部通过（附 2 处"因上游抖动无法判定"的明示），反向验证 5/5。
>
> **调参过程本身是一条教训**：我先给 recall 层设了"容许 2 个文档差异"的**绝对阈值**，
> 实测漂移在 2~6 之间波动 → 误报；改成 15% **比例** → 仍偶发误报；改成 30% → 仍偶发。
> 最后才想明白：**对一个上游近似索引的输出设任何硬阈值都会周期性误报**。
> 改为"只报警不判失败"，并把安全网建立在**入参断言 + 最终返回断言**上 ——
> 这两处都是严格的，recall 真退化（如传错 k）依然会被抓到。
>
> **"无法判定"必须显式报出来**：如果分级比对只输出"通过"，会掩盖掉"其实有一大段没验证到"。
> 所以 `TraceComparison` 把 `advisories` 与 `failures` 分开，摘要里也带上条数。
>
> **补测发现的一个真实缺口**：反向验证时我构造了"`fed` 判定永远为真"的缺陷，
> 但原有测试没抓到它 —— 因为那些用例里 recall **没有**抖动（`volatile_drifted=False`），
> `fed` 的对错不影响结果。补了一条"recall 抖动 + 不吃 recall 输出的阶段也变了"的用例
> 才覆盖到。**这正是"缺陷注入要挑对触发条件"的价值**：测试全绿不等于覆盖到了关键路径。

### P2 — 魔数散落 + 路由名单硬编码，调参和扩展都危险

**证据**：

- 硬编码阈值分布：`retriever.py`（`SCORE_THRESHOLD=0.06`、`_RERANK_EXPAND_FACTOR=5`、`_CACHE_TTL=300`）、`fusion.py`（`_KG_TEXT_BOOST=1.2`、`_PARENT_WINDOW_BONUS=1.08`、`_HYDE_PENALTY=0.95`）、`postprocess.py`（`_RRF_K_BASE=20`、`_NOISE_MIN_COVERAGE=0.15`）、`reranker.py`、`bm25.py` 等数十个。
- `_resolve_retrieval_policy` 里**硬编码了 14 个路由名**的列表，而路由权重的真源在 `recall.py:_ROUTE_WEIGHTS`。**两处名单各自维护，必然漂移**——新增路由后阈值校准会静默漏算该路由。

**为什么是问题**：调参需要改代码 + 重启 + 重新评测；阈值不可观测、不可 A/B；路由名单漂移导致校准失真且无任何报错。

**改进方案**：

- 把**检索质量相关**的常数（阈值、权重、倍率）集中到 `core/settings.py`，允许通过 `.env` 覆盖。运行时可调是调优的前提。
- 路由名单改为**从 `recall.py` 导出**（`ACTIVE_ROUTES = tuple(_ROUTE_WEIGHTS 的键集合)`），消除第二处真源。
- 为每类阈值加一个"最后校准时间 + 依据"注释，并在 §1 P0 第二步的质量回归测试里覆盖它们。

- 前端 `static/app.js`（391 行）**零测试、零 lint**。
  > **现状更新（2026-09-19）**：`app.js` 已增至 700 行；**测试已补齐** ——
  > 见附录 A #19（`tests/test_frontend_smoke.py`，7 条 Playwright 用例）。
  > **lint 仍为零**：项目只配了 Python 侧的 ruff，前端没有 eslint / prettier，
  > 因此"前端缺静态检查"这个判断**依然成立**。

**改进方案**：

- **测试金字塔落地**：单元（纯函数，快，多）→ 集成（链路，用 fake 依赖，中）→ 端到端（真实 HTTP + fake 模型，少）。当前"倒金字塔"要摆正。

### P2 — Chroma 索引落盘竞态：入库后立即查询会间歇性失败

**证据**（本轮建立检索门禁时实测）：向 ChromaDB `add_documents` 之后**立即**查询，
会间歇性抛：

```
Error executing plan: Internal error: Error creating hnsw segment reader: Nothing found on disk
```

**间歇性正是它危险的地方。** 同一份代码连续运行：

- 命中的集合**每次都不同**（实测在 `computer_organization` / `operating_system` 之间随机）。
- 命中后该集合**整轮不可查询**：该学科的检索结果全部来自别的学科，但不报任何错。
- 门禁指标会从 `category_hit@1` 0.900 掉到 0.725、`empty_result_rate` 从 0 升到 0.025 ——
  **看起来完全像一次严重的检索退化**，让人去改本来没坏的代码。

**本轮把根因查到了哪一步**（三条实测结论，都是"排除法"）：

| 检查项 | 结果 |
|---|---|
| `_ensure_hnsw_params` 是否在新建集合上调用 `modify()` 触发重建？ | **否** —— 打点确认 `needs_update=False`，`modify()` 从未执行。**排除** |
| 集合数据是否真的丢了？ | **否** —— `count()` 正确（如 419），HNSW 元数据 `status=ok` |
| 「丢弃 `_stores` 缓存句柄」能否恢复？ | **不能** |
| 「重开 `chromadb.PersistentClient`」能否恢复？ | **不能** |
| 「`delete_collection` + 重新入库」能否恢复？ | **能** |

**结论**：向量确实写进去了，但该集合的 **HNSW 段文件从未落盘**；进程内没有任何办法
把它"等"出来。这是 ChromaDB 写入侧的缺陷，**不是本项目可以靠重试绕过的**。

**已落地的处理（分层，而不是假装修好了）**：

1. **`VectorStoreManager.wait_until_ready`** —— 明确定位为**检测器而非修复器**。
   它把"静默返回错误检索结果"变成"入库期显式失败"，并在错误信息里直接给出补救命令
   （`ingest_category(<集合>, rebuild=True)`）。文档里写清了三种恢复手段的实测结果，
   避免后来者再去试"重试/重开 client"这两条死路。
2. **`rag/ingest.py`** —— 每个分类入库后做就绪检查；不可查询时记录 `not_ready` 并
   以 ERROR 级汇总（附补救命令），不再让故障无声通过。
3. **`rag/ingest.py` 的预热告警** —— `warmup_query_cache` 的成功率低于
   `settings.WARMUP_MIN_SUCCESS_RATE` 即判为异常，进日志（ERROR）与指标
   （`ingest_warmup_summary`）。此前只打印一行 INFO。
4. **门禁侧自动重建** —— `retrieval_gate.wait_for_index_ready(repair=True)`：
   门禁的索引是一次性的，重建无副作用，所以对不可查询的集合**只重建它自己**后重试。
   生产路径 `repair=False` —— 那里删集合意味着真实数据丢失，必须人工确认。

> **这一条同时说明了门禁的第一个真实价值**：它没抓出检索退化，却抓出了一个此前无人知道
> 的上游缺陷 —— 因为它是这个项目里第一个"**每次都在全新索引上跑完整链路**"的自动化流程。
> 既有的单测都在 mock 依赖，永远跑不到这条真实路径。这印证了 §1 P0 的判断：
> **测试真空的代价不是"没测试"，而是"没人知道代码实际在做什么"。**
>
> **✅ 根因已定位并修复（后续轮次）—— 先前的"未闭环"结论已被推翻。**
>
> **根因：读锁只接了一半。** `VectorStoreManager` 的 `_rw_lock` 给写路径
> （`add_documents`）和就绪探测都加了锁，但**生产唯一读路径 `_raw_search`
> 直接调 `store.similarity_search_with_score`，完全绕过读锁**。
> AST 枚举确认：manager 那个加锁读方法只有一个调用者 —— 就绪探测自己。
> **这把读锁在生产里是死代码。**
>
> 这解释了全部迷惑性症状：**就绪探测能过而首个真实查询失败**（探测加锁、真查询不加）、
> 命中的集合随机（看哪个集合还在落盘）、`delete` + 重建能修好（重建出一致的段）。
>
> **与上游 issue #4212 的区分（关键）**：报错完全一致，上游根因是
> `Collection.query` 会**意外变更集合维度**，由 PR #4224 修复。但我们跑在 **1.5.9**，
> 远晚于修复版本 1.0.2 —— **所以不是同一个 bug**。这个区分决定了修法方向：
> **不是"升级依赖就好了"，而是自己代码的锁没接全。**
> 如果停在"找到了上游 issue"就收工，会得出错误的结论。
>
> **修法**：`_raw_search` 改走 `get_vector_store_manager().similarity_search_with_score(...)`。
> 门禁六项逐位一致；反向验证（改回绕过读锁）→ **3 条测试全部变红**。
>
> **残留风险（如实记录）**：本次修的是**并发互斥**。若 Chroma 在写锁释放**之后**
> 仍异步落盘，读锁拦不住 —— 就绪屏障作为第二道防线保留。
>
> **调试方法论**：先尝试直接复现（全量建索引 1 次 + 小集合 add→query 12 次）**都没复现**；
> 于是**改用静态证据** —— AST 枚举调用点 + 比对加锁路径，直接看出锁没接全。
> **"复现不了"不等于"查不出根因"，换一种证据类型（静态 vs 动态）往往更快。**

> **Q&A 链路实测结论（后续轮次，沙箱实验，已还原）**
>
> 原判断是"`_ANSWER_RE` 匹配不到真题标注，改正则即可"。**实测后发现这个判断不完整**：

> 1. **题干+答案+解析本来就在同一个 chunk 里** —— 每个真题 chunk 都含 `✅` 与解析。

>    `merged_qa_meta` 路由**恒返回空** —— 确认是死代码。
> 3. **阻断点至少三个，不是一个正则**：
>    - `_ANSWER_RE` 匹配不到真实标注（`**解析**：` / `✅`）→ 实测 **0 命中**；
>    - `_EXAM_Q_HEADING_RE.match()` 要求 `#` 前缀，但 `section["heading"]` 是
>      **去掉 `#` 的标题**（实测 `'第1题(数据结构·选择题)'`）→ **恒为 False**；
>    - **即使前两个都打补丁修好，`merged_qa` 仍然一个都不产出** ——
>      `has_qa_chunk` / `is_qa` 那条路径上还有第三个阻断点。
>
> **成本/收益（沙箱实测）**：
>
> | | |
> |---|---|
> | 收益 | 让权重 2.0 的 `merged_qa_meta` 路由生效，习题/答案/对比类查询时真题 chunk 被二次命中加权 |

### 本轮的方法论教训：日志与 stdout 交错会伪造「空结果」

记录在这里，因为它比任何单个缺陷都更容易重复踩到。

排查"数据结构类 query 是否返回空"时，我用
`python probe.py 2>&1 | grep -v "Async Chroma query failed"` 过滤日志噪声，
结果看到 6 条 `ds` query **完全没有命中行**，于是得出"`data_structure` 检索整体失效"的结论。

**这个结论是错的。** 真实原因是：logging 走 stderr、`print` 走 stdout，两者
**按行交错**；当一条证据行与一条日志行落在同一物理行上时，`grep -v` 会把整行一起删掉。
"没有输出"其实是"被我自己的过滤器删掉了"。

把结果改成 **JSON 落盘**后复测：40 条 query **零空结果**，`ds` 类全部命中 `data_structure`。

**由此得出两条硬性要求**（已同时写进 §3.1 评审要点）：

1. **凡是"统计/测量"脚本，结果一律走结构化输出（JSON/CSV）落盘，不要靠人眼读 stdout。**
   过滤日志噪声的操作，本质上是在不可靠的信道上做减法。
2. **看到"零结果 / 全失败"这类极端结论时，先怀疑测量工具，再怀疑被测系统。**
   极端结论应该先被复现一次（换个观测通道），再写进报告。

## 2. 团队能力短板与最佳实践规范

### 2.1 短板诊断（从代码痕迹反推，非主观评价）

代码是团队思维方式的化石。从本项目痕迹看，四个可复用的能力缺口：

**短板一：会写"能跑的复杂逻辑"，不会写"可验证的复杂逻辑"**

`retrieve_documents` 447 行、`aretrieve_documents` 427 行、`split_documents` 230 行——能写出来说明**业务理解和技术能力都不差**。但覆盖率 7%/0% 说明：面对"异步 + 多路并发 + 外部依赖"的复杂场景，团队**不知道从哪下刀写测试**，于是选择不写。

> 根因：缺乏"**先设计可测边界，再实现逻辑**"的习惯。测试写不出来，往往是因为函数边界本身没设计好——447 行的函数无法测，不是测试的问题，是设计的问题。

**短板二：抽象与分解的粒度感不足**

团队会做**横向分层**（agents/rag/core 分得很清楚），但**纵向分解**不足——同一个模块内部动辄 400+ 行函数。这说明抽象停在"模块级"，没下探到"函数级职责单一"。

**短板三：异常处理策略是"兜底"而非"设计"**

92 处 `except Exception` 反映一种心态：**怕崩，所以全都接住**。但"接住"不等于"处理"。真正的工程判断是：哪些错误该重试、哪些该降级、哪些该让用户看到、哪些必须让系统崩掉（fail-fast）。项目里其实**已经有正确答案的样本**——`supervisor.py` 的 `UnclosedSpecialistOutput` 就是优秀的 fail-fast 设计。**把这种思路推广到全项目**，就是提升点。

**短板四：把类型系统当负担，而不是当工具**

用"整目录关闭检查"解决类型报错，而不是"修好类型或精确豁免"。这与 `settings.py` 里认真写 `Annotated[str, BeforeValidator(...)]` 形成鲜明对比——**团队里有懂类型的人，但没形成共识和规范**。

**短板五：性能与成本意识有设计、无度量**

项目里有丰富的超时常量、token 预算、多级缓存——设计意识是好的。但**没有任何性能测试、没有 token 用量统计、没有缓存命中率的观测面板**（`_cache_stats_fields` 收集了数据却没人消费）。**做了防护，但不知道防护是否生效**。

### 2.2 最佳实践规范（团队工程宪法）

以下规范**全部针对上述短板**，可直接执行。

#### 规范 1：函数与模块规模红线

| 对象 | 上限 | 超出处理 |
|---|---|---|
| 单函数 | 60 行 | 拆分为阶段函数；确需超出须在 PR 说明理由 |
| 单文件 | 600 行 | 按职责拆模块 |
| 单函数参数 | 5 个 | 改用 dataclass / Pydantic 模型传参 |
| 嵌套深度 | 4 层 | 提取早返回（early return） |

**为什么是 60 行**：一个函数超过一屏，评审者无法在脑中完整推演其所有分支——**不可评审的代码等于没有评审**。

> **⚠️ 后续核实：这条规范此前没有任何执行机制。** 实测（2026-09-22）：
> **8 个文件超 600 行**（`retriever.py` **1908** / `imputer.py` 1348 / `splitter.py` 1214 / …）、
> **54 个函数超 60 行**（`split_documents` **240** / `_semantic_segment` 183 / `fuse_evidence` 179 / …）。
> **规范没有执行机制，等于没有规范** —— 与「保护机制存在 ≠ 生效」同源。
>
> **✅ 已加棘轮门禁**：`tests/test_structure_ratchet.py` + `tests/_structure_baseline.json`。
> 规则与 `C90 max-complexity` 同一思路 —— **冻结现状、阻止新增**：
> 不在基线里的文件必须 ≤600 行、函数必须 ≤60 行；在基线里的条目**只能变小不能变大**
> （基线必须与实测一致，否则测试会提醒你收紧）。
> 反向验证：从基线移除条目 → 断言精准变红。**探针已从 `_semantic_segment` 换成
> `split_documents`** —— 前者修好之后不再是超标函数，探针随之失效、那条元测试自己红了
> （见 backlog #36 的教训：「探针要挑短期不会被修好的对象」）。
>
> **为什么不一次性重构掉这 53 个函数**：§4.2 阶段二把这件事列为 **6–8 周**工作量。
> **旧债按计划逐步还，新债一律不许进。**（09-23 的首笔还债见 §0 现状快照与 §3.4。）

#### 规范 2：分层异常处理

```python
# 1) 定义域内异常层级（不要用字符串传递错误语义）
class RagError(Exception): ...
class RetrievalUnavailable(RagError): ...   # 依赖不可用 → 可重试/可降级
class RetrievalEmpty(RagError): ...         # 正常空结果 → 不记 ERROR
class RagInternalError(RagError): ...       # 代码缺陷 → 必须告警

# 2) 禁止裸 pass
except SomeError:
    logger.debug("...", exc_info=True)   # 必须留痕
    # 注释说明为何此处忽略是安全的

# 3) catch-all 只允许在最外层边界，且必须分级
try:
    ...
except (RetrievalUnavailable, TimeoutError) as e:   # 预期内失败 → 降级 + WARNING
    return _degraded_result(e)
except Exception:                                    # 非预期 → ERROR + 上报
    logger.exception("unexpected failure in retrieval")
    raise

# 4) fail-fast 优先于兜底
#    数据契约被破坏时（如专家输出未闭环），宁可崩也不要静默降级
#    参照 agents/supervisor.py: UnclosedSpecialistOutput
```

#### 规范 3：可测试性作为设计约束（而非事后补救）

- **纯逻辑与副作用分离**：计算逻辑写成纯函数（输入 → 输出），I/O 与外部调用放在薄壳层。本项目 `_apply_rerank_threshold`、`weighted_rrf_merge` 就是正面样本。
- **依赖注入**：外部依赖（LLM / embedding / 存储）必须可替换。项目已有 `USE_FAKE_MODEL`、`get_store()` 注入模式，**新代码必须遵循**。
- **每个新增/修改的函数，PR 必须附带其测试**。无法测试的代码，说明边界设计有问题，先重构再提交。
- **禁止"为了测试而 mock 掉被测逻辑本身"**：mock 只用于外部依赖，不用于被测对象。

#### 规范 4：配置外置与单一真源

- 所有**可调参数**（阈值、权重、倍率、预算）进 `core/settings.py`，`.env` 可覆盖；代码中只允许存在"算法内生的数学常量"（如 `RRF k=60`）。
- **同一份数据只允许一个真源**。路由名单、模型清单、prompt 版本等，禁止在第二个地方复制列表（现有 `_active_routes` vs `_ROUTE_WEIGHTS` 就是反例）。
- 新增配置项**必须同步 `.env.example`**（已有约定，继续执行）。

#### 规范 5：可观测性

- 日志分级要有语义：`ERROR` 只用于"需要人介入"的事件；预期内的降级用 `WARNING`；正常空结果用 `INFO`。
- **关键路径必须可追踪**：检索链每一步（召回数量、融合分数、rerank 分数、是否命中缓存）已有 INFO 日志——保持，并补齐指标消费（把 `_cache_stats_fields` 接到 `/health` 或 `/metrics`）。
- 每个 catch-all 必须能回答："出问题时，日志能不能让我定位到具体环节？"

#### 规范 6：异步与并发

- 同步阻塞调用**禁止出现在 async 函数中**，必须 `asyncio.to_thread` 包装（项目已有 `_safe_to_thread` 工具，继续用）。
- 所有外部调用**必须有超时**；所有并发分支**必须有失败隔离**（`as_completed` + 单分支异常不拖垮整体，`_multi_route_search` 已是正面样本）。
- 共享可变状态（缓存、全局单例）必须线程安全且**有界**（`BoundedCache` 是标准做法）。

#### 规范 7：安全

- 密钥一律 `SecretStr`，取值 `.get_secret_value()`，**禁止出现在日志/异常消息里**。
- 所有来自客户端、可能访问他人数据的标识（如 `thread_id`）**必须校验归属**（`_check_thread_owner` 是标准做法）。
- 外部输入一律经 Pydantic 校验；前端输出必须转义（`static/app.js` 需明确 XSS 转义策略）。

## 3. 代码质量把控标准

### 3.1 代码评审要点（Reviewer Checklist）

**评审者的职责是"把关"而非"挑刺"。按以下顺序检查，前项不过不进入后项：**

**A. 正确性（Blocking）**
- [ ] 边界条件：空输入、空结果、超长输入、None 是否处理？
- [ ] 并发安全：共享状态是否加锁/有界？异步中是否有阻塞调用？
- [ ] 错误路径：异常是否被正确处理（分层、留痕、不吞）？失败时状态是否一致？
- [ ] 外部依赖：是否都有超时？失败是否隔离（不拖垮主流程）？
- [ ] 契约变更：对外接口（`schema/`）改动是否向后兼容？改了是否同步调用方与文档？

**B. 可测性（Blocking）**
- [ ] 新增/修改逻辑是否有对应测试？测试是验证**行为**还是只验证**调用**？
- [ ] 是否引入了难以测试的设计（长函数、硬编码依赖、隐藏状态）？
- [ ] 覆盖率是否覆盖到本次改动的分支（而非整体数字）？

**C. 可维护性（Blocking）**
- [ ] 函数是否 ≤ 60 行、文件 ≤ 600 行？超限是否有正当理由？
- [ ] 命名是否表达意图（`data`/`temp`/`result2` 一律打回）？
- [ ] 是否有解释"为什么"的注释（而非复述代码的"是什么"）？
- [ ] 是否违反单一真源（复制了列表/常量/逻辑）？

**D. 性能与成本（重要）**
- [ ] 是否引入了额外的 LLM 调用 / 检索调用？能否复用缓存？
- [ ] token 预算是否受控（长文本拼接是否有上限）？
- [ ] 是否有 N+1 式的串行外部调用（应并发）？

**E. 安全（Blocking）**
- [ ] 密钥/敏感信息是否泄漏到日志或响应？
- [ ] 客户端可控的标识是否做了归属/权限校验？
- [ ] 输入是否经校验？输出是否转义？

**F. 一致性（建议）**
- [ ] 是否遵循 CLAUDE.md 的既有约定（配置走 settings、LLM 走工厂、注册 agent 同步三处）？
- [ ] 类型注解是否完整（新增代码不得依赖目录级放宽）？

**G. 验证方法（Blocking，本轮新增 —— 全部来自真实踩过的坑）**
- [ ] **"没报错"是否被当成了"环境是封闭的"？** 评测/门禁类改动的验收标准必须包含
      "它依赖哪些外部资源"，并在**无外部资源的条件下**跑一遍。
      （本轮实测：`USE_FAKE_MODEL=true` 下检索链仍调用**真实 LLM**，
      本地每次结果不同、CI 直接崩 6/40 条 —— 全程无任何报错。）
- [ ] **门禁自身的噪声是否测量过？** 连续跑 N 次确认可复现，再定容差。
      若噪声 ≥ 容差，那不是门禁，是随机数生成器。
      （本轮实测：`hit@1` 噪声 0.025 > 容差 0.02，根因是 RRF 并列排序依赖线程完成次序。）
- [ ] **"连续 N 次一致"是否可能只是巧合？** 本轮把连续 4 次一致当成了"确定性已修复"的证据，
      但当时基线跑在真实 LLM 上 —— 那是巧合。**要说明为什么它应该一致，而不只是观察到它一致。**
- [ ] **测试断言是否"恒真"？** 构造输入时要确认它真的能触发被测分支。
      反例：让两个文档各占一条同权重同 rank 的路由 → 分数并列，
      `scores == sorted(scores, reverse=True)` 恒真，测不出排序方向。
      **反向验证是唯一可靠的检出手段。**
- [ ] **缺陷的严重性是否用真实数据量过？** 合成用例能证明"存在这条路径"，
      证明不了"这条路径有多重要"。（本轮实测：全库留存率 97.6%，
      362 个"丢失" section 里 318 个是只有标题的空 section。）
- [ ] **"修复"是否被端到端指标验证过？** 单测全绿 + 审查通过 ≠ 端到端没退化。
      涉及数据/检索的改动必须过端到端指标。
- [ ] **测量脚本结果是否走结构化输出落盘？** 不要靠人眼读 stdout，更不要用 `grep -v`
      从混合日志里"减"出结论 —— logging 走 stderr、print 走 stdout 按行交错，
      会把证据行一起删掉，制造出"检索返回空"的假象。
- [ ] **注入/恢复脚本是否用原始字节备份？** 若备份取自"已规范化换行"的文本，
      恢复时会把 CRLF 改成 LF，而"两边都规范化后再比较"的校验**必然通过**。
- [ ] **新增门禁/断言前，是否测量过它自身的噪声？** 连续跑 N 次确认结果可复现，
      再决定容差。**若噪声幅度 ≥ 容差，那不是门禁，是随机数生成器。**
      （本轮实测：检索门禁的 `hit@1` 噪声约 0.025 > 容差 0.02，
      根因是 RRF 并列排序依赖线程完成顺序 —— 详见 §1 P1。修掉不确定性后噪声归零。）
- [ ] **测试断言是否"恒真"？** 构造输入时要确认它真的能触发被测分支。
      本轮两处反例：让两个文档各占一条同权重、同 rank 的路由 → 分数并列，
      于是 `scores == sorted(scores, reverse=True)` 恒真，测不出排序方向；
      以及用 2 个元素验证"按 key 升序"的约定 —— 任何确定性次级键都可能碰巧给出同序。
      **反向验证是唯一可靠的检出手段。**
- [ ] **缺陷的严重性是否用真实数据量过？** 合成用例能证明"存在这条路径"，
      证明不了"这条路径有多重要"。本轮教训：我用手写的短例题推出"严重内容丢失"，
      实测全库留存率 97.6%，且 362 个"丢失" section 里 318 个是**只有标题的空 section**
      —— 过滤它们是正确行为。**先量分布，再定优先级。**
- [ ] **"修复"是否被端到端指标验证过？** 本轮我修了一个逻辑自洽、三个新测试全绿的
      "原子单元被合并"问题，门禁显示留存率 97.6%→96.5%、精确率 0.9014→0.8952
      —— 已回退。**单测全绿 + 审查通过 ≠ 端到端没退化**，涉及数据/检索的改动必须过端到端指标。

> **评审节奏建议**：单次 PR ≤ 400 行改动。超过则要求拆分——**评审质量与改动规模成反比**。

### 3.4 CI 门禁增强建议

现状（`.github/workflows/test.yml`）已覆盖 lint / format / type / test / cov / docker / md lint，很完整。建议增补：

1. **分模块覆盖率门槛**：`pytest --cov=src/rag --cov-fail-under=70` 等，避免整体数字掩盖风险。
2. **改动覆盖率（patch coverage）从 informational 改为阻塞**：`codecov.yml` 目前 `patch.informational: true`，意味着**新代码可以零测试合入**。改为 `informational: false` + `target: 80%`——这是"新债不再产生"的关键闸门。
3. **复杂度门禁**：接入 `ruff` 的 `C90`（mccabe）规则或 `radon`，对超阈值函数报警。
   ✅ **已落地**：`extend-select` 加 `C90`，阈值取 **= 当前最复杂函数的复杂度**（开启时命中 0 处）。
   **刻意做成"棘轮"而不是一步到位**：设常见的 15 会一次命中 11 处既有代码、门禁立刻变红，
   结果要么被 `noqa` 绕过要么被关掉 —— 那就失去了意义。含义是
   「**不许再写出比今天最复杂的那个还复杂的函数**」，新债被拦、旧债不动。
   ★ **09-23 收紧：30 → 25**（backlog #36，先把最复杂的降下来再调阈值）：
   `_semantic_segment` 30 → ≤24（183 行 → 薄编排 + 6 个步骤函数）；
   `_chroma_window_expand` 与 `message_generator` 各 26 → ≤25。
   ★ 现在**恰为 25 的有两个**（都零余量）：`_impute_heading` 与 `message_generator` —— 下次收紧的目标。
5. **结构规模门禁（新增）**：`C90` 只管**复杂度**，不管**规模** —— 规范 1 的
   600 行 / 60 行红线此前完全没有执行机制（实测 8 文件 + 54 函数超标）。
   ✅ **已落地**：`tests/test_structure_ratchet.py` + `tests/_structure_baseline.json`，
   同一「棘轮」思路：基线冻结现状，新代码必须合规，已有条目只能变小。
   更新基线：`python tests/test_structure_ratchet.py`（**变大即回退，应在 review 中被质疑**）。
4. **检索质量回归**：✅ **已落地**（本轮）——新增独立 job `retrieval-quality-gate`，
   跑 `uv run python -m evaluation.retrieval_gate`，不依赖任何外部服务，耗时约 35s。
   与覆盖率门禁互补：覆盖率保证"代码被跑过"，它保证"跑出来的结果没变差"。
5. **依赖安全扫描**：`uv.lock` 已有锁定，建议加 `pip-audit` 或 Dependabot。
   ✅ **已落地（选 Dependabot）**：新增 `.github/dependabot.yml`，覆盖四个生态
   （`uv` / `github-actions` / `docker` / `pre-commit`），按周提 PR。
   **关键设计是分组（groups）**：把同类 minor/patch 更新合成**一个** PR ——
   否则一周刷出十几个 PR，很快就没人看了，**没人看的 PR 等于没有**。
   major 更新被 `ignore` 掉、单独处理（可能带破坏性变更）。
   > 备选 `pip-audit` 未采用：它需要在 CI 里多装一个依赖并新增 job；
   > Dependabot 是零依赖的纯配置，且顺带覆盖 Actions / 基础镜像 / 钩子版本。

> **门禁设计原则**：门禁应当**阻止新增债务**，而不是**逼人还清旧债**。旧债用计划逐步还（见 §4），新债一律不许进。

> **门禁的第一个真实收益（本轮实测）**：检索门禁上线后，它**没有**抓到检索退化，
> 却抓出了一个此前无人知道的环境竞态（Chroma HNSW 落盘未完成即查询 → 间歇性失败，
> 详见 §1 P2）。原因是它是这个项目里第一个"**每次都在全新索引上跑完整链路**"的自动化流程 ——
> 既有的单测都在 mock 依赖，永远跑不到这条真实路径。
> 这印证了 §1 P0 的判断：**测试真空的代价不是"没测试"，而是"没人知道代码实际在做什么"。**

- **验收**：能独立产出一份被采纳的工程标准或架构决策文档。

### 4.3 配套机制（比路线图更重要）

技术能力不会因为"看了文档"而提升，只会因为"**在真实约束下反复做判断并被反馈**"而提升。

1. **结对评审（每周 1 次，30 分钟）**：随机抽一份本周 PR，两人对读，重点讲"**为什么这么设计**"而非"语法对不对"。资深者要示范"如何提出建设性意见"。
2. **故障复盘（每次线上问题）**：不问"谁写错了"，只问"**为什么这个错误能被写出来且没被测出来**"。产出必须落到"门禁/测试/规范"的改进，而非"下次注意"。
3. **技术分享（每两周 1 人）**：讲本项目的真实难题——比如"多路召回为什么用 RRF 而不是加权求和""同步/异步双份实现如何统一"。**讲自己的代码是最好的学习**。
4. **轮值 owner**：每周一人负责"质量门禁"——检查新 PR 的 patch coverage、是否有新增 `except: pass`、函数是否超限。**让每个人都当过"守门人"**，规范才会内化。
5. **读优秀代码**：把本项目 `supervisor.py`（fail-fast 设计）、`core/llm.py`（缓存与状态陷阱）、`core/cache.py`（有界缓存 + 淘汰回调）当作**内部教材**——团队里已经有人能写出好代码，**让其他人读懂它，比看外部文章更有效**。

### 4.4 一句话总结

> 这个团队**不缺技术能力，缺的是质量纪律的覆盖面**。
> 提升的关键不是"学更多技术"，而是把已有的好习惯（清晰的注释、防御性设计、fail-fast）**从"某些模块"推广到"所有模块"**，尤其是那个承载全部产品价值、却最缺乏保护的检索链。

> `BM25_CANDIDATE_FACTOR` / `BM25_CANDIDATE_FLOOR` 后，**一个进程只建一次索引**，

>
> ①②③（**全部是假 embedding**，字符 bigram 哈希）都显示 `FACTOR=5` 有明确收益：
> ① `hit@1` +5pp / `precision` +0.0051；② +2.5pp / +0.0061；③ +2.5pp / +0.0096。

> 主要来源，放宽它就能改变排序；真实 embedding 提供了真正独立的语义信号，融合排序不再由 BM25
> 候选池决定。**所以「放宽候选池能改善排序」只在假 embedding 下成立。**
