### 1.5 ★ M1 的证据：相对阈值的净效果

逐条重算 `_apply_rerank_threshold`（阈值 = `max(top1 × 0.3, 0.15)`，`min_keep = 2`）：

| # | 打分文档数 | top1 | 阈值 | ≥阈值 | 最终 context 中低于阈值的条数 |
|---|---|---|---|---|---|
| 5 | 2 | 0.9772 | 0.2932 | 1 | **1（0.0957，被强留）** |
| 15 | 2 | 0.2348 | 0.1500 | 1 | **1** |
| 17 | 2 | 0.4096 | 0.1500 | 1 | **1** |
| 18 | 2 | 0.7023 | 0.2107 | 1 | **1（0.0512，被强留）** |
| 20 | 2 | 0.0054 | 0.1500 | 0 | **2（整份 context 全部低于绝对阈值）** |
| 其余 15 条 | — | — | — | 全部 ≥ 阈值 | 0 |

- 凡 `≥阈值` 的条数 < 2 的情形，`min_keep=2` 兜底返回 `reranked[:2]`，把低分文档**原样还原**。
- 其余情形里，所有 reranked 文档**本就** ≥ 阈值。

⇒ **从最终证据集合看，相对阈值删除 0 条、强留 6 条。**
V1 §0.1 的「6 条 rank2 被相对阈值筛掉」与明细不符（被"筛掉"的文档其实都还在）。

**可观测边界（必须诚实标注）**：阈值在 `rerank()` 返回的 `top_n` 列表**内部**是否删除过文档，明细看不到 ——
这正是 M2 要补的盲区。

### 1.6 ★ M2 的证据：被漏掉的那道漏斗

```
召回(RRF) ──► 去重 + 阈值 ──► rerank()  ──► _apply_rerank_threshold ──► 窗口展开 ──► 最终
                                  │
                                  └─ top_n = min(top_k, len(documents))
                                     top_k = k*2 (分解) else k
                                     ⇒ 只返回 top_n 条，其余**直接丢弃**
```

`_stage_rerank` 把 `rerank()` 的返回值交给 `_apply_rerank_threshold`。
因此**正确文档若落在 top_n 之外，阈值阶段根本看不到它** —— 「阈值杀掉正确答案」在机制上不可能。

#4（concept, k=5 → top_n=5）与 #18（code, k=6 → top_n=6）的正确文档，
在明细里都**不在最终 context 中**，且其同类文档分数低于同批其它文档 ⇒ 流失点在 **`rerank()` 的排序/截断**，不是阈值。

### 1.7 其他被明细直接证实的问题

1. **排序不变量被违反**：`#20` 的 `ctx0` 是 `rerank_score=0`、无 `recall_routes` 的窗口填充物，**却排在 `ctx1`（0.0054）之前**。

3. **指标判定力弱**：`ctxP` 与 `ctxR` **13/20 完全相等**；`ctxP` 分布 = `{1.0: 10, 0.0: 8, 0.3333: 1, 0.8333: 1}`。
4. **`formula` / `table` chunk 确实被检索到**，但走的是 `semantic` / `focus`，**不是** `formula_meta` / `table_meta`。

## 2. 零成本验证协议（本方案的核心）

**原则**：凡是能用确定性、零 token 手段判定的，绝不用 RAGAS。RAGAS 只回答一个门禁答不了的问题 ——
「检索变好，答案是否真的更准？」

| 层 | 手段 | 成本 | 回答什么问题 |
|---|---|---|---|
| **L0** | **TEI `/rerank` 离线直探** | **0**（本地） | A1/A2 改动后，目标 chunk 的 rerank 分数/名次是否上升、是否进 top_n、是否过阈值 |
| **L1** | **候选追踪探针**（新增 `evaluation/candidate_trace.py`） | 0 | 每条 probe 的候选**在哪一层消失**（召回 → 去重 → rerank top_n → 阈值 → 最终） |
| **L2** | `evaluation.retrieval_gate`（5 条路由） | 0 | 检索管线是否退化 |
| **L3** | `evaluation.stage_trace` | 0 | 阶段级行为是否等价 |
| **L4** | RAGAS | **付费** | 端到端答案质量 |

### 2.1 L0：TEI 直探的可行性已被证明

V1 诊断 §4 已实测：把**从索引取出的真实 `page_content`** 过 TEI `/rerank`，结论可复现（§4D 批效应已排除），
且模型校准正常（相关 0.9925 / 无关 0.00002）。

**因此 A1/A2 的 A/B 可以完全离线做**：

```
对每条 probe（query + 正确 chunk_id）：
  取该 chunk 的真实 page_content
  ├─ 原始形态            → TEI /rerank → score / rank
  └─ A1/A2 变换后形态     → TEI /rerank → score / rank
  判据：score 是否跨过 max(top1×0.3, 0.15)，且是否进入 top_n
```

**这不消耗任何 LLM token，且比 RAGAS 精确**（直接看目标文档的名次，而不是端到端均值的稀释效应）。

### 2.2 L1：候选追踪探针（新增，M2 的直接产物）

`evaluation/stage_trace.py` 只记录**阶段间接口**，不记录**候选身份在阶段内的去留**。
需要新增一个探针，对固定 probe 集打印：

```
recall           : N 条  | 目标 chunk 是否在池？rank?
dedup+threshold  : M 条  | 目标是否仍在？
rerank top_n     : T 条  | 目标是否在 top_n 内？rerank 分？
apply_threshold  : K 条  | 目标是否通过？若未通过，是否被 min_keep 还原？
expand           : F 条  | 目标是否仍在？是否被填充物挤出？
```

**输出契约**：每条 probe 一行 JSON，字段含 `target_chunk_id` / `stage` / `present` / `rank` / `score` / `dropped_by`。
`dropped_by` 是**枚举**（`not_recalled` / `dedup` / `rrf_threshold` / `rerank_topn` / `rel_threshold` / `window_budget`），
不允许是自由文本 —— 自由文本会让"在哪一层丢的"退化成猜。

**这是本方案第一个要做的东西**，因为它把 M1/M2 的分歧变成可判定的事实。

2. **门禁结果**：至少真实 embedding 路由；触及 rerank 时必须真实 TEI rerank；
3. **反向验证**：故意移除新逻辑，目标 probe 应回退；
4. **回滚安全**：先保存变更前的候选轨迹，绝不用「指标不变」作为成功理由；
5. **RAGAS**：仅在 §4.4 条件全绿时跑，且必须带 `details`，用逐条配对比较。

## 7. 一句话

**V1 把主矛盾定位在「rerank 之后的阈值」，明细复算显示阈值净删除为 0 —— 真正的漏斗是
`rerank()` 的 `top_n` 与 `min_keep` 的强留，方向相反、且都在阈值之外。
本方案的第一个动作不是改代码，而是把候选追踪探针装上，让「在哪一层丢的」从推断变成枚举。**
