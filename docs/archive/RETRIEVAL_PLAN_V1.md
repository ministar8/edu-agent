# EDU-Agent 检索层治理方案

> **定位**：本文件是 `docs/RETRIEVAL_ROADMAP.md`（效果路线图）的**执行方案**：把路线图里的判断落到具体任务。  
> **依据**：2026-09-24 全链路实测（阶段触发率 / 关键开关行为 / 各阶段耗时 / 路由贡献度，均为实测非估算）。  
> **执行约定**：每个任务给「改哪里 + 验收标准 + 风险」；验收标准必须是**可判定的数字或可观测行为**。  
> **与路线图的关系**：路线图回答「做什么、为什么做」；本文件回答「先做哪个、做完怎么判定」。

## 0. 2026-09-26：逐条明细驱动的正式执行顺序（当前权威）

> **取代范围**：本节取代本文旧 §3/§4 中「先上游数据、后 RRF」的执行排序；旧章节保留为历史
> 背景与已完成记录。依据是 `evals/results/ragas_baseline20_qwen37_flash_details.json`（20 条查询、83 条最终证据）的逐条证据、候选流失插桩与 TEI 直接探针。
>

### 0.2 阶段 A：先修 rerank 输入与筛选策略（主路径）

**目标**：在不改召回/RRF 的前提下，让“已经被召回的正确候选”能经 rerank 留到最终 context。

| A 项 | 做法 | 改动边界 | 对照实验 | 通过标准 | 回滚条件 |
|---|---|---|---|---|---|
| **A0 固化排序探针** | 将 #4、#18、#17 变成确定性检索回归样例；记录候选池身份、RRF 分、rerank 分、最终 rank、是否通过阈值 | 只加 `evaluation/` 探针/断言 | 当前生产口径 | 每次都能回答“正确文档在哪一层丢失” | 不改变运行时 |
| **A1 术语归一化 A/B** | 只给 reranker 的 query 建别名扩展（如“折半查找 ↔ 二分查找”）；原始 query 仍用于检索与生成 | rerank 输入层，不改知识库原文、不改 RRF | 原始 rerank query vs 规范化 rerank query | #4 正确 chunk 的 rerank rank 上升且通过最终筛选；非目标 probe 不退化 | 目标样例未提升或引入错误首位 |
| **A2 代码候选说明 A/B** | 对 `code_mixed` 候选仅在**送入 reranker**前增加结构化说明（主题/代码用途/“以下为伪代码”）；不改向量库正文 | reranker 文本构造层，先不重入库 | 原始代码文本 vs 说明前缀 + 原代码 | #18 的正确代码 chunk 留在最终证据；代码类 probe 的正确命中不下降 | 非代码候选或原文交付被污染 |
| **A3 筛选策略 A/B** | 将“相对阈值 + 无条件 `min_keep=2`”拆开评估：绝对下限、保底数量、保底触发条件必须可观察 | `_apply_rerank_threshold` | 固定候选池上的策略矩阵；再跑真实检索探针 | #4/#18 保住正确候选；#5/#20 不再把全低分噪声强塞给 LLM；空结果不增加 | 任一安全 probe 变为空，或错误文档抢首位 |

**A 阶段纪律**：

1. A1/A2 **先于** A3：若 reranker 本身把正确候选打成 0.0037/0.0576，单降阈值只会把更多噪声一起放进来。
2. A3 不允许“拍脑袋改全局常量”。先固定候选池，枚举策略，再选择在 #4/#18/#5/#20 上同时满足约束的方案。
3. `rerank_score` 要区分三种语义：真实打分、L1 未重排的 0、窗口填充的 0；不可把它们混进同一分布做阈值结论。

### 0.3 阶段 B：small-to-big 从“追加文档”改为“受控组装”

**问题边界**：窗口展开不是 #4/#18 主要失败点，但它造成 19/83 未打分填充、22/83 零分证据，必须在排序稳定后处理。

| B 项 | 做法 | 通过标准 |
|---|---|---|
| **B1 明确锚点/填充契约** | 每个展开文档带 `anchor_id`、`expanded_from`、`anchor_rerank_score`；不得伪装成独立召回命中 | 明细可区分锚点和填充物，所有填充物可追溯到一个锚点 |
| **B2 parent 级组装 A/B** | 同一 `parent_id` 的锚点和相邻 chunk 合并为一份上下文，而非多条 score=0 Evidence | `#16` 类同 parent 重复从 3 条压到 0；最终 Evidence 中不再出现无路由的独立填充项 |
| **B3 排序不变量** | 展开物不得排在它的锚点之前；无合格锚点时不得触发扩展 | #20 类低分填充不会排第一；context 中每份内容都有可解释的锚点 |

**验收口径**：优先看“同 parent 冗余率”“无 `recall_routes` 独立 Evidence 数”“锚点前置率”，不要只看 context 总条数。

### 0.4 阶段 C：学科路由，先证实再约束

| C 项 | 做法 | 对照实验 | 通过标准 |
|---|---|---|---|
| **C0 路由原因追踪** | 对主查询与每个子查询记录：分类、关键词命中、推断集合、追加集合、最终候选集合 | 不改行为 | #9/#17/#19 能解释每个集合为何进入或缺席 |
| **C1 缺主学科回退** | 当分类/关键词产生单一集合但该集合与稳定主学科信号冲突或召回为空时，设计“保留/补搜主学科”的窄规则 | 原逻辑 vs 补搜/软约束 | #9 重新出现 OS 证据；非目标查询的正确集合首位不下降 |
| **C2 软约束 A/B** | 只在“主查询已确定学科、子查询无明确新学科信号”时继承；显式新信号允许跨科 | 无约束 vs 软约束 | 减少 #17/#19 类越界，不压制真实跨科问题 |

**明确不做**：不直接把所有子查询锁死在单一学科。跨科本身不是错误，#9 是“正确学科缺席”，#17/#19 才是噪声案例。

### 0.5 阶段 D：metadata 路由只做可观测性和存活分析

逐条明细只能看到**最终** `recall_routes`，不能判断 `formula_meta` / `table_meta` 为零是：

1. 路由未生成；2. 路由查询为空；3. Chroma 返回空；4. 返回但 RRF/阈值/rerank 筛掉。

因此先补每条 metadata 路由的四段计数：`generated → queried → returned → final_survived`，按 `query_type` / `collection` 输出。

| 决策规则 | 后续动作 |
|---|---|
| 路由从未 generated | 修分类/触发条件，不加正文约束 |
| generated 但 returned=0 | 核对 metadata 值/过滤条件/数据入库 |
| returned>0 但 final=0 | 回到阶段 A 的排序分析 |
| 全段都有贡献但质量差 | 才评估“metadata 正文相关性约束”A/B |

### 0.6 并行数据轨：明确区分“知识库缺”与“检索缺”

| 数据项 | 证据 | 动作 | 检索验收不应承担 |
|---|---|---|---|
| 单链表就地逆置 | 知识库只有一行概念、无实现 | 补算法说明 + C/伪代码 + O(1) 空间说明 | 不能要求检索召回不存在的内容 |
| HTTP GET 客户端 | 网络知识库几乎无 socket/HTTP 客户端实现 | 补最小客户端步骤、请求格式、错误处理边界 | 同上 |
| section.path 脏/长/重复 | 37/83 不可读，影响 rerank 输入但不是 #4 主因 | 先做**派生的 rerank 文本规范化** A/B；未经收益验证不批量重写原知识库标题 | 不以文件改动数量验收 |

### 0.7 阶段 E：最后才做 RRF

**前置条件全部满足才开始**：

- A 阶段正确候选不再因 rerank/阈值流失；
- B 阶段没有未排序填充物污染最终 Evidence；
- C 阶段能解释集合选择；
- D 阶段知道 metadata 路由的真实流失位置；
- 有至少 2 个“正确候选在 RRF 之前就不存在或被 RRF 错排”的复现案例。

若这些条件拿不出来，**不启动跨集合 RRF 实验**。现在 #4 的正确候选在 RRF rank 2、#18 在 rank 7，流失点都在 RRF 后，直接改 RRF 无法修主矛盾。

### 0.8 统一验收与运行顺序

```
P0  A0  固化可复现 probe / 候选流失追踪（零运行时改动）
    ↓
P0  A1  同义词 rerank query A/B
    ↓
P0  A2  code_mixed rerank 文本 A/B
    ↓
P0  A3  阈值 + min_keep 策略矩阵 A/B
    ↓
P1  B1-B3  受控 small-to-big 组装
    ├────────→ P1 数据轨：补 #16/#20 内容（可并行）
    ↓
P1  C0-C2  学科路由可观测性 → 窄回退 → 软约束
    ↓
P2  D      metadata 路由存活分析
    ↓
P3  E      仅在出现 RRF 前流失/错排证据后，做 RRF 实验
    ↓
[用户明确批准后] 对稳定的最终方案跑 RAGAS；禁止在每一个小 A/B 后重复跑
```

### 0.9 每一步必须交付的证据

每个阶段变更都必须给出：

1. **固定 probe 表**：目标 query、正确来源、候选池 rank、rerank rank/score、最终是否保留；
2. **门禁结果**：至少真实 embedding 路由；如果触及 rerank，必须真实 TEI rerank；
3. **反向验证**：故意移除新逻辑，目标 probe 应回退，证明测试能抓住改动；
4. **回滚安全**：先保存变更前的候选轨迹，绝不使用“指标不变”作为成功理由；
5. **RAGAS**：仅在用户明确要求时跑，且每次保存带 `details` 的同口径结果文件，不能用只有均值的输出替代。

## 2. 问题清单（按层）

### 度量层（尺子）

1. 学科级 `category_hit_at_k = 1.0000` **饱和**，零余量
2. `kp_hit@k` 只&#x5230;**「章」级** —— 节/小节级无度量
3. 默认路由跑**假 embedding** → 默认口径下一切结论都是伪影
4. 真实 embedding 路由需 TEI 且**不进 CI** → 语义质量无人守
5. **RAGAS 全量 40 条从未跑**（只有 probe n=1 / smoke n=5）→ 答案级空白
6. 黄金集 **40 条全是概念题** → 出题 / 批改 / 代码类查询零覆盖
7. `kp_annotated` 只 40 条，扩量到 150~200 未做

### 链路自身

1. 耗时 **89.1% 集中在「多路召回 + 融合」** —— 单点热点未优化
2. `decompose` **30 次调用只有 9 次真拆** —— 21 次空转，代价未测
3. **HyDE 在黄金集 0 触发** → 兜底代码**从未被真实执行过**（未被验证）
4. `verifier` 的 **LLM 校验层全仓 `use_llm_verify=False`** —— 死代码
5. **`merged_qa` 的 104 chunk 无任何路由利用**（96 条 qa 字段完整）—— 白存
6. 「标准答案独立存储」的设计意图**落空**（`answers` 集合从未创建）
7. `content_type` 是**单值形状分类器**，无法承载语义
8. **`detect_content_type` 规则顺序使 `exercise`/`answer` 不可达** —— 本轮用独立标志**绕过**，该函数本身仍坏
9. 分解专用 RRF 权重 **1.5 : 1.0 硬编码未校准**
10. 主 RRF 的 `_dynamic_rrf_k` 与 13 条路由权重**未校准**

### 数据层（知识库）

1. **12.5%（245/1960）标题含噪声**，有的标题**是一整段话**
2. 知识点粒度 **1199 个 / 2205 chunk（≈1:1）**，不成层
3. `splitter` 产出的 `section.path` **带 `[]` 包装**（读取端已兼容，格式本身未统一）
4. **`merged_qa` 只覆盖讲义、不覆盖真题**（`_ANSWER_RE` 认不出真题的 `✅ + **解析**`）
5. `learning_paths` 只有 **24 chunk**，覆盖极薄

### 观测层

1. `STAGE_TARGETS` 覆盖不全 —— 本轮已补 `fuse_rrf_main` / `fuse_documents` / `verify`
2. `hyde_added_count` 语义不准（记截断前候选数，≠ 净增条数）—— 本轮已修
3. 路由贡献度此前**只在临时脚本里统计**，未进门禁 —— 本轮已进报告与基线 `_meta`

### 0.4 根因与修复：追踪入口到不了证据层（2026-09-24 已修）

`STAGE_TARGETS` 里 `fuse_documents` / `verify` 的目标写对了

**问题在于验机制用的入口，不是录基线用的入口。** 两个函数在追踪链路上永远不被调用：

```
record_query()  →  R.aretrieve_documents()        ← 追踪入口走的是「文档层」
                     └─ _stage_classify / decompose / recall_and_merge
                        / dedup / rerank / hyde / expand_windows
                     ✗ 从不触及 fusion / verifier

afuse_documents / averify_evidence 只在 aretrieve_evidence() 里被调用  ← 「证据层」
（retriever.py:1744 / 1775 / 1839 / 1842 / 1875，均为函数内局部导入）
```

门禁走的是 `aretrieve_evidence_with_retry`（会到证据层），追踪走的是  
`aretrieve_documents`（到不了）—— **两者覆盖的不是同一条链路**。

否则补的是一个永远为 0 的指标 —— 它比不补更危险：看着像「已覆盖」，实际是新的盲区。


（同类：只加日志不打点、只加断言不触发。）

## 9. RAGAS 的定位与跑法（2026-09-24 决定）

### 9.1 决定

**只跑一次，作为「最终效果陈述」；不做 before / after 对比。**

理由：RAGAS 的价值不是诊断，而是陈述。诊断检索层问题由**门禁 + 阶段追踪**承担
（零 token、确定性、且能定位到具体 query 与阶段）。

### 9.2 RAGAS 到底测什么：4 个指标分属两层

按**输入**拆开看，它并非「4 个都测检索」：

| 指标                 | 输入含 contexts | 测哪层        |
| ------------------ | ----------- | ---------- |
| `context_recall`   | ✅           | 检索层（召回）    |
| `context_precision` | ✅           | 检索层（精度）    |
| `faithfulness`     | answer + contexts | 生成层（有无幻觉）  |
| `answer_relevancy` | 只有 answer   | 生成层（是否切题）  |

**它不能定位问题**：给的是端到端**均值**，不说明哪条 query 错、错在第几个阶段；
连「检索错」还是「生成错」都分不干净 —— `faithfulness` 低可能是模型幻觉，
也可能是检索没给对材料。

### 9.3 与门禁的分工

| | 检索门禁（0.3 / 0.4） | RAGAS（0.2） |
|---|---|---|
| 测什么 | 检索结果的**位置**（目标学科 / 章是否在前 k） | 端到端**答案**质量 |
| 判据 | 黄金集标注（subject + knowledge_points） | reference + judge LLM |
| 成本 | **0 token**，约 90 秒 | 全量约 **290 万** token，30~60 分钟 |
| 稳定性 | 确定性 | judge LLM 有随机性 |
| **能否定位** | **能**（逐条 outcome + 阶段追踪） | **不能** |
| 用途 | 回归防护 / 找检索问题 | 效果陈述 |

### 9.4 因此：0.2 从「阶段 0 的尺子」改为「阶段 3 之后的验收」

阶段 1~3 全是**检索**改动，它们的尺子是**门禁** —— 而门禁恰好在本轮升级过：
0.1 把黄金集从 40 条扩到 156 条、覆盖 4 类查询，`kp_hit@k` 从饱和的 0.9250
变成有区分度的 0.7179。**所以阶段 1~3 不必等 RAGAS。**

RAGAS 要回答的是最后一问：**检索变好，答案是否真的更准？**
这一问门禁答不了（它只看位置，不看答案），所以放在最后。

### 9.5 运行前提：TEI embedding 必须可用

`cli._preflight` 在真实 embedding 不可用时**阻塞并返回退出码 2**（实测
`http://localhost:11435/embeddings` → 502）。`--skip-preflight` 无效（检索会抛
`RetrievalUnavailable`）；`USE_FAKE_EMBEDDING=true` 能跑但结论是伪影
（见 `ARCHITECTURE.md` §6.2(c)：假路由 +5pp、真实路由收益为零）。
故 **0.2 依赖 TEI 恢复**。

### 9.6 待定：跑多少条

全量 156 条最省事（无需解释抽样）；若控成本，用 `--sample-per-type N`（分层等距抽样）。
**不要用 `--limit`** —— 实测 `--limit 40` 取到的是 40 条纯概念题（类型成块排列），
「每类前 N 条」又会偏向 ds/co（类型块内按学科成块）。

成本随 n 线性（单样本约 1.85 万 token）：每类 15 条（60 条）≈ **111 万**；全量 ≈ **290 万**。

### 10.2 1.1 的两条设计决定

**(a) `【】` 内容整体删除。** 实测 173 处里 **145 处是「考点」**，其余是重点/技巧/总结/
真题年份等**同类分类标记**。它们横跨大量 chunk，是检索上的高频低区分度 token ——
保留等于给每个 chunk 加一个共同前缀。标题因此改为纯粹的语义短语。

**(b) 机械规则 + 27 条手工拆分。** 机械规则处理 243 条简单情形；另 27 条
（18 条超长 + 5 条同形态「标题=段落」+ 4 条整条标题就是 `【...】`）逐条手工写
「短标题 + 正文」，写在脚本的 `LONG_FIX` 里，可逐条审阅。

**★ 踩到的坑：宽松正则会改坏代码。** 初版用 `^(#{1,6})\s*`（允许 `#` 后无空格）匹配标题，
实测把 **90 行代码**误判成标题 —— `#include <stdio.h>`、`#define MaxSize 10`、
汇编注释 `#jump when equal...`、`#等价于：`。若按标题规则改写，就是**直接破坏代码块**。
CommonMark 要求 `#` 后有空白，正则必须是 `^(#{1,6})[ \t]+`。

### 10.3 1.2 的根因有两层（计划只写了一层）

**第一层：`_ANSWER_RE` 认不出真题的写法。** 真题用 `✅` 标正确选项、用 `**解析**：`
（加粗夹在词与冒号之间），原正则 `(?:解答|答案|正确答案)[：:]` 两处都匹配不到。
修法：加 `解析` 与 `✅` 两个分支。`✅` 实测**只出现在 `knowledge/questions/`**（讲义 0 处），
故对讲义的 `has_answer_marker` 零影响。

**第二层（更隐蔽）：`has_qa_chunk` 是假信号。** 真题 section 的首行 `### 第N题(…)` 会被切成
一个 **17 字的 `is_qa` 块**，它随即被 `MIN_CHUNK_LENGTH=80` 过滤掉；但兜底分支的判据是
「有没有 QA 块」而不是「有没有**可用**的 QA 块」，于是判据为真、兜底不触发，
正文落进 else 分支变成 `detail`，`qa.*` 字段全空。
**修法**：判据改为「存在长度 ≥ `MIN_CHUNK_LENGTH` 的 `is_qa` 块」。
> 只改第一层的话，`content_type` 会变成 `merged_qa` 而 `chunk_role` 仍是 `detail` ——
> **看着达标、实则 Q&A 字段仍是空的**。这正是「验收标准必须能分辨真假达标」的又一例。

**附带修 `_ANSWER_KEY_RE`**：真题不写「答案：」，若不认 `✅` 所在选项行，
`qa.answer_key` 会全空 —— 而选择题的自动批改正是靠这个字母。修后 **240/273** 有值
（每年正好 40 道选择题），其余 33 条是综合应用题（本就无字母答案）。

### 10.5 ★ 重录基线的陷阱：`--update-baseline` 会记录故障态

`disabled` 路由**第一次**重录时出现 **16 条空结果**（`cat@k` 0.7949 → **0.5705**，
`empty` 0 → **0.1026**）；**复跑则完全正常**（0.7692 / empty 0）。

原因：门禁的 `report_retrieval_anomalies` **只拦「抛异常」的查询，静默返回空不拦** ——
而 `empty_result_rate` 只是一个带容差的**指标**，`--update-baseline` 不做合理性检查，
于是故障被**直接写进基线**。这与门禁文档串反复强调的「静默返回空是最危险的退化形态」
是同一个盲区，只是这次出现在**录制侧**而不是**判定侧**。

**已做的补救**：三条 fake 路由各**独立复跑 2 次**，结果逐位一致，确认当前基线是健康态。

> **操作纪律**：重录基线后必须检查 `empty_result_rate` 与量级是否合理，
> **不能只看「命令成功」**。建议给 `--update-baseline` 加一条硬校验
> （`empty_result_rate > 0` 或指标偏离上次基线超过某阈值时拒绝录制）—— 列入待办。
