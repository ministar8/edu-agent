> 数据来源：`evals/results/ragas_baseline20_qwen37_flash_details.json`
> 口径：真实 `BAAI/bge-m3` embedding + 真实 TEI `bge-reranker-v2-m3` rerank，judge/generation = `qwen3.7-flash`
> 复现环境：本机 TEI `:11435` / `:11436` 均在运行

## 0. 结论先行

**检索链的失败发生在 `rerank` 层，不在召回、不在 RRF、不在跨学科。**

正确文档**已经进了候选池**，但 reranker 给它极低的分数，随后 `_apply_rerank_threshold` 的
相对阈值（`top_score × 0.3`）把它筛掉。两例实测：

| 查询 | 正确答案 | 候选池位置 | rerank 分 | top 分 | 阈值 | 结局 |
|---|---|---|---|---|---|---|
| #18 生产者-消费者伪代码 | `06_代码实现.md::生产者进程` | 121 条中 rank 7 | **0.0037** | 0.7025 | 0.2108 | **被筛** |
| #4 折半查找的适用条件 | `07_查找.md::❗2.1 二分查找` | 76 条中 rank 2 | **0.0576** | 0.4265 | 0.1500 | **被筛** |

**reranker 低分的两个可复现原因**（TEI 直探实测）：

1. **中文同义词鲁棒性差** —— 同一段内容，术语写「折半查找」得 **0.9732**，写「二分查找」得 **0.0577**（差 17 倍）。
2. **纯代码 chunk 打分 ≈ 0** —— 纯代码 **0.0080**；加一句含「伪代码」的自然语言说明后 **0.3510**。

> 部署模型确认无误：`/data/bge-reranker-v2-m3`（TEI 1.7.4），校准正常（相关 0.9925 / 无关 0.00002）。
> 所以这是**能力/阈值适配问题**，不是配置错误。

**除 rerank 之外，明细文件里还暴露出 7 个独立的检索层问题**（完整清单见 §5）：

| # | 问题 | 规模 |
|---|---|---|
| 1 | **产出量系统性不足** | 83/105 条证据，**13/20 条查询拿不满 k** |
| 2 | **未重排的展开填充物占 22.9%** | 19/83 条 `_window_expanded` + `rerank_score=0` + 无 `recall_routes` + 同 parent 重复 |
| 3 | **阈值两头失控** | 6/20 条 rank2 被误杀；同时 `min_keep=2` 强行保留不合格文档（`#20` 整份 context 全低于绝对阈值） |
| 4 | **集合路由 1 条致命 + 2 条越界** | `#9` 期望学科**根本没被检索** → `ctxR=0` |
| 5 | **4 条元数据路由零贡献** | `answer_meta` / `comparison_meta` / `formula_meta` / `table_meta` |
| 6 | **section.path 45% 不可读** | 37/83 含 `❗`/`**`/`【` 或超长；含「标题即段落」与术语重复 |
| 7 | **L1 路径不做相关性排序** | `#3` 走 `l1_fast`，3 条证据 `rerank_score` 全 0 |

## 1. 先修数据口径：两个结果文件不是同一次运行

| 文件 | 时间 | faith | ctxP | ctxR | ansRel |
|---|---|---|---|---|---|
| `ragas_baseline20_qwen37_flash.json` | 11:14 | 0.7317 (n=20) | **0.4208** | **0.4208** | 0.5024 |
| `..._details.json` | 11:43 | 0.6874 (n=18) | 0.5583 | 0.4430 (n=19) | 0.6302 |

两次之间 `src/evaluation/*` 被改过（11:20~11:22）：`adapters` 增加 details 返回 + `build_judge_llm`
显式同步三处 timeout；`config` / `dataset` 增加 `sample_per_type` 分层抽样。

- **明细是当前口径；汇总文件应视为废弃**，引用前需重跑。
- 汇总文件里 `ctxP == ctxR`（0.4208 / 0.4208 完全相等）在明细里并不相等 —— 该巧合未解释。

**指标判定力弱（这本身是个要先解决的问题）**：

- `context_precision`：20 条里 **8 条 = 0.0、10 条 = 1.0**，仅 2 条中间值
- `context_precision` 与 `context_recall` **13/20 完全相等**

→ 用这两个指标做 A/B 实验会非常迟钝。**在它们之上做「优化效果」判定，风险很高。**

## 3. 逐阶段插桩：候选在哪一层消失

真实 embedding + 真实 rerank，与 RAGAS 那次同口径。包装 `_stage_recall_and_merge` /
`_stage_dedup_and_threshold` / `_stage_rerank`，**打印文档身份而非只打印条数**。

### #18 `用信号量写出生产者—消费者问题的伪代码。`

```
① recall_and_merge          : 121 条   ← 正确答案 06_代码实现.md::生产者进程 在池（rank 7）
② dedup + threshold(0.12)   :  24 条   ← 正确答案仍在池
③ rerank                    :  24 → 2 条
      0.7025  02_进程管理.md :: ❗5.2 生产者-消费者（散文）        ← 保留
      0.0037  06_代码实现.md :: 生产者进程（纯代码，就是答案）      ← 被筛
   阈值 = max(0.7025 × 0.3, 0.15) = 0.2108
```

### #4 `折半查找的适用条件是什么？`

```
① recall_and_merge          :  76 条   ← 正确答案 07_查找.md::❗2.1 二分查找 在池（rank 2）
② dedup + threshold(0.08)   :  23 条   ← 正确答案仍在池
③ rerank                    :  23 → 3 条
      0.4265  07_查找.md :: 2.2插值查找（不是答案）              ← 保留
      0.0576  07_查找.md :: ❗2.1 二分查找（就是答案）            ← 被筛
   阈值 = max(0.4265 × 0.3, 0.15) = 0.1500
```

**两例机制完全相同。** 另注：`_stage_dedup_and_threshold` 实测把 121→24、76→23 砍掉约 80%
（`effective_threshold` = 0.12 / 0.08），这是**第二道**漏斗，但本例正确答案都过了这一关。

## 4. reranker 低分的直接原因（TEI 真实探针）

用**从索引取出的真实 `page_content`** 过 reranker（手打文本会得出相反结论 —— 见下）。

### A. 纯代码 chunk（query：`用信号量写出生产者—消费者问题的伪代码。`）

| 形态 | rerank |
|---|---|
| 纯代码（真实形态，242 字） | **0.0080** |
| 标题 + 一句「…的伪代码实现如下：」+ 代码 | **0.3510** |
| 纯自然语言描述（无代码） | 0.0019 |
| 自然语言描述 + 代码 | 0.0054 |

### B. 折半查找 chunk（query：`折半查找的适用条件是什么？`）

| 形态 | rerank |
|---|---|
| 真实入库文本（术语 = **二分查找**） | **0.0577** |
| 同内容，术语换成 **折半查找** | **0.9732** |
| 干净标题 + 折半查找 | 0.9987 |
| 干净标题 + 二分查找 | 0.5322 |
| 去掉 `**` / `❗` 噪声 | 0.0443（**没救**） |
| 截掉标题里的长正文 | 0.1109（**没救**） |

**结论**：

1. **同义词不匹配是主导因素**（0.0577 ↔ 0.9732）。干净标题只能救到一半（0.5322）。
2. **纯代码 chunk 打分 ≈ 0**，且加自然语言说明的**内容**不救，加含「伪代码」字样的**措辞**才救（0.0080 → 0.3510）。
3. **去噪声、截短标题都救不了** → 「标题即段落」（见 `docs/RETRIEVAL_PLAN.md` §2 数据层第 18 条）
   **不是 #4 低分的主因**，虽然它确实是内容缺陷。

### C. TEI 直调校准（绕开项目代码）

```
query = 折半查找的适用条件是什么？
  折半查找的前提是线性表中的记录必须关键码有序，且线性表必须采用顺序存储结构。  → 0.9925
  二分查找是一种高效的查找算法。                                            → 0.0217
  今天的天气很好，适合出门散步。                                            → 0.00002
```

→ **模型工作正常**，问题在「同义词鲁棒性」+「纯代码形态」+「相对阈值过严」三者叠加。

### D. 批效应已排除

| 对照 | 单独 | 在批次里 |
|---|---|---|
| `07_查找.md::❗2.1` | 0.0576 | 0.0573（31 条批次） |
| `06_代码实现.md::生产者进程` | 0.0037 | 0.0037（26 条批次） |

→ **分数稳定，不是批内归一化伪影。** 固定阈值与相对阈值都可按静态分布理解。

## 5. 检索层问题清单（从明细文件完整抽取，83 条证据 / 20 条查询）

### 5.0 产出量：系统性地拿不满 k

| 指标 | 值 |
|---|---|
| 证据总数 / 应得 | **83 / 105**（code 类 k=6，其余 k=5） |
| 拿不满 k 的查询 | **13 / 20** |
| 最终 context 条数分布 | `{2:3, 3:5, 4:4, 5:4, 6:2, 7:2}` |

### 5.1 ★ 约 23% 的上下文是「未重排的展开填充物」

`_window_expanded=True` 的证据 **19/83**，它们同时满足三个特征：

- `rerank_score = 0`（**从未进入重排**）
- **无 `recall_routes`**（不是任何召回路由选中的）
- 与另一条证据**同 `parent_id`**（同一小节被拆成多个 chunk）

**核算闭合**：19（展开填充）+ 3（`#3` 走 L1 路径，整条不做重排）= **22/83 = 26.5% 的证据 `rerank_score = 0`**。

两个典型：

```
#16 单链表就地逆置  5 条 context
  ctx0  score=0.5748  02_线性表.md::4.3销毁链表     ← 不是答案
  ctx1  score=0.2015  02_线性表.md::三、双链表
  ctx2  score=0.0  expanded 无routes  parent=...::25  ← 填充（同 ctx0 的 parent）
  ctx3  score=0.0  expanded 无routes  parent=...::25  ← 填充
  ctx4  score=0.0  expanded 无routes  parent=...::25  ← 填充
  → 5 条里 3 条是同一个（且错误的）小节的冗余填充

#20 HTTP GET 客户端  3 条 context
  ctx0  score=0.0  expanded 无routes  05_传输层.md::1.5 传输流程   ← 填充，且排第一位
  ctx1  score=0.0054                  05_传输层.md::1.5 传输流程
  ctx2  score=0.0045                  04_网络层.md::3.7 路由聚合
  → 三条全部低于绝对阈值 0.15，整份 context 都是兜底产物
```

**危害**：这些填充物**未经过任何相关性筛选**，却与已选中的证据同属一小节 → 只增加 token、不增加信息，并稀释 `context_precision`。

### 5.2 ★ 相对阈值与 `min_keep` 兜底，两头都失控

`_apply_rerank_threshold` 的阈值 = `max(top1 × 0.3, 0.15)`。实测：

| # | top1 | top2 | 落差 | 阈值 | rank2 结局 |
|---|---|---|---|---|---|
| 5 | 0.9772 | 0.0957 | **0.8815** | 0.2932 | **被阈值杀掉** |
| 18 | 0.7023 | 0.0512 | **0.6511** | 0.2107 | **被阈值杀掉** |
| 19 | 0.9294 | 0.3591 | 0.5703 | 0.2788 | 保留 |
| 17 | 0.4096 | 0.0323 | 0.3773 | 0.1500 | **被阈值杀掉** |
| 16 | 0.5748 | 0.2015 | 0.3733 | 0.1724 | 保留 |
| 10 | 0.7192 | 0.3646 | 0.3546 | 0.2158 | 保留 |
| 15 | 0.2348 | 0.0074 | 0.2274 | 0.1500 | **被阈值杀掉** |

**共 6 条查询的 rank2 被阈值杀掉**（#3 / #5 / #15 / #17 / #18 / #20）。
reranker 的分数分布**非常陡**（top1 与 top2 常差 0.4~0.9），而相对阈值是 `top1 × 0.3` ——
**top1 分越高，阈值越高，第二名越容易被误杀**。

**反向失控**：`#5` 的 `ctx1` 只有 **0.0957**（远低于阈值 0.2932）却仍被保留 —— 说明
`min_keep=2` 的兜底在**强行保留不合格文档**。于是阈值**该杀的没杀干净、不该杀的杀掉了**。

### 5.3 集合路由：1 条致命 + 2 条越界

| # | 问题 | 详情 |
|---|---|---|
| **#9** | **期望学科根本没被检索** | `请出一道考查磁盘空闲空间管理的题。`（OS）→ 实际只搜了 `questions`，**`operating_system` 集合完全没进** → `ctxR = 0.00` |
| #17 | 跨学科 | CO 查询带进了 `operating_system`（1 条，且是错误章节） |
| #19 | 跨学科 | OS 查询带进了 `data_structure`（1 条，`06_图.md::参考` 链接页） |

其余 **17/20 正常**。根因：`_infer_subject_collections` 靠关键词表匹配，无关键词时退化全 4 科
（#17）；有关键词但匹配错学科时**不会回退**（#9）。

### 5.4 4 条元数据路由在本 20 条内零贡献

`recall_routes` 里从未出现的元数据路由：

```
answer_meta · comparison_meta · formula_meta · table_meta
```

**但** `formula`（5 条）与 `table`（6 条）chunk 确实被检索到了 —— 说明它们是靠
`semantic` / `focus` 拿到的，**这两条精准路由没有被用上**。

对照：`exercise_meta` 贡献 **12 次**（全部是 `questions:exercise_meta`）—— 上一轮修活的那条路由
在 generate 类查询上确实在大量工作。

### 5.5 section.path 质量：45%（37/83）不可读

含 `❗` / `**` / `【` 或超长（>90 字）的章节名 **37 条**。最差样本：

```
#17 [八、文件系统基础 > 4.**【考点】文件的物理结构物理结构**:就是在操作系统看来,文件的数据
     是如何存放在外存中的。操作系统需要对磁盘块进行管理。(**文件分配方式**)]
     ← 章节名里塞了一整段话

#2  [... > 1.2 广度优先遍历广度优先搜索 > 1.2.1 广度优先搜索算法]     ← 术语重复
#14 [... > 7.调度算法的**评价指标中央处理器利用率** > 8.2.1时间片轮转时间片轮转]  ← 术语重复
#3  [存储系统 > ❗8.高速缓冲存储器高速缓存 > 8.1局部性原理]            ← 术语重复
```

这些标题随 `page_content` 进入 reranker 输入。实测影响见 §4 B：**术语/标题形态会让分数变化约 2×**
（0.0577 → 0.1109 / 0.5322），但**不是主导因素**（同义词不匹配才是，差 17×）。

### 5.6 L1 路径不做相关性排序

`#3`（`Cache 的作用是什么？`）走 `l1_fast`：3 条证据 **`rerank_score` 全为 0**（整条跳过重排），
分数仅 0.123~0.156。该条指标碰巧不错（ctxP/ctxR = 1.0），但**没有任何排序保障** ——
一旦命中的 section 偏了，L1 没有任何机制纠正。

### 5.7 code 类的证据形态正撞 reranker 的弱点

code 类 20 条证据的 `content_type`：`code_mixed` **10** / `section` 7 / `text` 3。

**一半是纯代码形态** —— 正是实测 `rerank ≈ 0.0037~0.0080` 的那一类（§4 A）。
`code` 类因此同时踩中「形态弱点」+「相对阈值过严」两个坑。

### 5.8 层分叉（记录，非缺陷）

```
code  → L3（4 条 l3_code + 1 条 l3_deep）
其余  → L2（18 条 l2_standard）+ L1（1 条 l1_fast，即 #3）
```

`#20` 走 `l3_deep`（因为被分类为 `is_structured`），但其证据分数全在 0.0045~0.0054。

| ⑤ 优化 small-to-big 上下文组装 | ⚠️ **不是这两个失败案例的原因**（失败发生在 rerank，早于 expand）。但有两个独立问题：<br>· **22.9% 的 context 是展开产物**（`score=0`），同一 `parent_id` 重复 2~4 次<br>· `corr(context 条数, ctxR) = 0.052` → **条数本身不是决定因素** |
| ⑥ 增加 metadata 正文相关性约束 | ❌ **数据不支持** —— metadata 路由**都在正常工作**（`code_meta` / `exercise_meta` 都召回了正确文件），问题在 rerank 排序 |
| ⑦ 最后再做跨集合 RRF 实验 | ❌ **数据不支持优先做** —— RRF 表现正常（把正确答案排到 rank 2 / rank 7）。失败发生在它**之后** |

**一句话**：计划的 ③~⑦ 里，数据只支持 ③ 的一部分；⑤ / ⑥ / ⑦ 都不是这两个失败案例的原因。
**真正的杠杆在 rerank 层。**
