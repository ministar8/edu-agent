## 学习目标

- 理解传输层的端到端角色
- 理解 TCP 连接、流量与拥塞思想
- 理解 UDP 的定位

---

## UDP

> section_id: basic-cn-transport-udp
> kp_ids: [cn.transport.udp]
> primary_kp: cn.transport.udp

**定义**：无连接、不保证可靠交付的用户数据报协议。

**为什么**：开销小、延迟低；适合可容忍丢失或自带可靠性的应用。

**思想**：把「是否可靠」交给应用选择。

---

## TCP 概述

> section_id: basic-cn-transport-tcp
> kp_ids: [cn.transport.tcp]
> primary_kp: cn.transport.tcp

**定义**：面向连接、可靠、字节流传输协议。

**为什么**：应用层不应自己解决丢失、乱序、重复问题。

**思想**：传输层提供**进程到进程**的端到端抽象，屏蔽网络层尽力而为。

---

## TCP 连接管理

> section_id: basic-cn-transport-tcp_handshake
> kp_ids: [cn.transport.tcp_handshake]
> primary_kp: cn.transport.tcp_handshake

**机制**：建立（三次握手）、释放（四次挥手）。

**为什么**：双方确认收发能力与序号起始，避免旧连接干扰；释放要双向关闭。

**思想**：可靠连接是**状态机 + 确认**，不是单纯「发消息」。

---

## 流量控制与拥塞控制

> section_id: basic-cn-transport-tcp_flow
> kp_ids: [cn.transport.tcp_flow, cn.transport.tcp_congestion]
> primary_kp: cn.transport.tcp_congestion

**流量控制**：接收窗口限制发送速率，防压垮接收方。

**拥塞控制**：网络整体过载时降速（慢开始、拥塞避免、快重传、快恢复等思想）。

**区别**：流量控是**收端问题**；拥塞控是**全网问题**。二者共同决定发送窗口。

## 端口号与复用分用

> section_id: basic-cn-transport-port
> kp_ids: [cn.transport]
> primary_kp: cn.transport

**端口号**：传输层用端口号区分同一主机上的不同应用进程，实现**进程到进程**的通信。端口号是传输层的服务访问点，16 位无符号整数，范围 0~65535。

**分类**：

- **熟知端口号**（0~1023）：由管理机构分配，如 HTTP=80、FTP=21、SMTP=25
- **登记端口号**（1024~49151）：需登记
- **短暂端口号**（49152~65535）：客户端临时使用

**复用与分用**：多个进程共用一个传输层协议**发送**数据称**复用**；接收方传输层把数据**分发给不同进程**称**分用**。

**常见熟知端口**：

| 协议 | 端口 | 传输层 | 用途 |
|---|---|---|---|
| HTTP | 80 | TCP | 超文本传输 |
| HTTPS | 443 | TCP | HTTP + 加密 |
| FTP | 21（控制）/ 20（数据） | TCP | 文件传输 |
| SMTP | 25 | TCP | 发送邮件 |
| POP3 | 110 | TCP | 接收邮件 |
| IMAP | 143 | TCP | 邮件访问 |
| DNS | 53 | UDP | 域名解析 |
| DHCP | 67 / 68 | UDP | 动态 IP 分配 |
| TFTP | 69 | UDP | 简单文件传输 |
| Telnet | 23 | TCP | 远程登录 |
| SSH | 22 | TCP | 安全远程登录 |

**思想**：网络层把分组送到主机（IP 地址），传输层用端口把数据送到进程；「IP 地址 + 端口」共同标识端到端通信的一端。

## UDP 与 TCP 的对比

> section_id: basic-cn-transport-udp-vs-tcp
> kp_ids: [cn.transport.udp, cn.transport.tcp]
> primary_kp: cn.transport.tcp

| 对比项 | TCP | UDP |
|---|---|---|
| 连接方式 | 面向连接 | 无连接 |
| 可靠性 | 可靠（确认、重传、序号） | 不可靠（尽最大努力交付） |
| 数据形态 | 面向字节流 | 面向报文，保留边界 |
| 流量控制 | 有 | 无 |
| 拥塞控制 | 有 | 无 |
| 通信模式 | 只能一对一 | 一对一、一对多、多对多 |
| 首部开销 | 20 字节（最小） | 8 字节 |
| 协议号 | 6 | 17 |

**数据单元**：TCP 传送 **TCP 报文段**，UDP 传送 **UDP 用户数据报**，二者统称运输协议数据单元 TPDU。

**思想**：TCP 用开销换可靠与有序，UDP 用最少开销换低时延与灵活，把「是否可靠」的选择权交给应用。

## UDP 首部格式

> section_id: basic-cn-transport-udp-header
> kp_ids: [cn.transport.udp]
> primary_kp: cn.transport.udp

**定义**：UDP 首部固定 8 字节，结构简单。

| 字段 | 长度 | 说明 |
|---|---|---|
| 源端口 | 16 位 | 发送方端口（可选，不使用时填 0） |
| 目的端口 | 16 位 | 接收方端口 |
| 长度 | 16 位 | 首部 + 数据的总长度，最小为 8 |
| 校验和 | 16 位 | 检验首部 + 数据（可选，不使用时填 0） |

**特点**：UDP 对应用报文既不合并也不拆分，保留报文边界；收到误码的数据报时只丢弃，不重传。

**思想**：首部越简单，处理开销越小；UDP 对差错「只报告、不补救」，把是否重传交由应用决定。

## TCP 首部格式与标志位

> section_id: basic-cn-transport-tcp-header
> kp_ids: [cn.transport.tcp]
> primary_kp: cn.transport.tcp

**定义**：TCP 报文段首部固定 20 字节，另可有可变长度选项。

| 字段 | 长度 | 说明 |
|---|---|---|
| 源端口 / 目的端口 | 各 16 位 | 发送方 / 接收方端口 |
| 序号 seq | 32 位 | 数据载荷第一个字节的序号 |
| 确认号 ack | 32 位 | 期望收到的下一个字节的序号 |
| 数据偏移 | 4 位 | 首部长度，单位 4 字节 |
| 标志位 | 6 位 | URG / ACK / PSH / RST / SYN / FIN |
| 窗口 | 16 位 | 接收窗口大小 rwnd |
| 校验和 | 16 位 | 检验首部 + 数据 |
| 紧急指针 | 16 位 | 紧急数据的末尾偏移 |
| 选项 | 可变 | MSS、窗口扩大、时间戳等 |

**标志位含义**：

- **URG**：紧急指针有效
- **ACK**：确认号有效（连接建立后为 1）
- **PSH**：接收方尽快交付应用层
- **RST**：复位连接
- **SYN**：同步位，建立连接时置 1
- **FIN**：终止位，释放连接时置 1

**要点**：SYN 置 1 的报文段不能携带数据，但要消耗一个序号；仅 ACK 置 1 的普通确认报文段可携带数据，不携带数据时不消耗序号。

**思想**：TCP 靠「序号 + 确认号 + 标志位」三者协作，把无序的 IP 数据报变成有序、可靠、可控的字节流。

## TCP 连接管理：三次握手与四次挥手

> section_id: basic-cn-transport-tcp-connection
> kp_ids: [cn.transport.tcp_handshake]
> primary_kp: cn.transport.tcp_handshake

**连接建立要解决的三件事**：确认对方存在、协商参数（如初始序号 ISN、最大报文段长度 MSS）、分配资源。

**三次握手**：

1. 客户端 → 服务器：SYN=1，seq=x（客户端选定的初始序号），进入同步已发送状态
2. 服务器 → 客户端：SYN=1，ACK=1，seq=y，ack=x+1，进入同步已接收状态
3. 客户端 → 服务器：ACK=1，seq=x+1，ack=y+1，双方进入连接已建立状态

**为什么需要三次**：可防止已失效的连接请求报文段突然到达服务器而导致错误——若只握手两次，服务器发出确认后即认为连接已建立，而客户端并未发起新连接，会白白占用服务器资源。

**四次挥手**：

1. A → B：FIN=1，seq=u（A 数据发完，请求关闭）
2. B → A：ACK=1，seq=v，ack=u+1（B 确认，进入半关闭状态）
3. B → A：FIN=1，ACK=1，seq=w，ack=u+1（B 数据也发完）
4. A → B：ACK=1，seq=u+1，ack=w+1（A 确认，之后等待 2MSL 再关闭）

**时间等待状态**：主动关闭方在发出最后一个确认后需等待 **2MSL** 再进入关闭状态，一是确保对方能收到最后的确认，二是让本次连接产生的所有报文段都从网络中消失，避免干扰下一个新连接。

**保活计时器**：连接建立后若长期收不到对方数据，服务器可据此探测并释放失效连接。

**思想**：可靠连接是**状态机 + 确认**——双方各自确认收发能力与序号起始，释放时需双向关闭（半关闭状态）。

## 超时重传时间的计算

> section_id: basic-cn-transport-rto
> kp_ids: [cn.transport.tcp]
> primary_kp: cn.transport.tcp

**问题**：RTO 太小会导致不必要的重传、增大网络负荷；RTO 太大会使重传推迟过久、降低传输效率，因此需根据 RTT 样本动态估算。

**平滑往返时间 RTTs**：

    RTTs = (1 − α) × 旧RTTs + α × 新RTT样本        （推荐 α = 1/8）

**偏差加权平均值 RTTd**：

    RTTd = (1 − β) × 旧RTTd + β × |新RTT样本 − RTTs|   （推荐 β = 1/4）

**超时重传时间 RTO**：

    RTO = RTTs + 4 × RTTd

**Karn 算法**：对重传的报文段不测量其 RTT 样本；发生重传时把 RTO 增大为原来的 2 倍（指数退避），不再重传时恢复正常计算。

**思想**：RTO 随 RTT 的均值与波动自适应——RTT 波动越大，RTO 越大，以避免把「慢」误判为「丢失」。

## 拥塞控制的四种算法与基础公式

> section_id: basic-cn-transport-congestion-algorithms
> kp_ids: [cn.transport.tcp_congestion]
> primary_kp: cn.transport.tcp_congestion

**发送窗口**：

    发送窗口 = min(拥塞窗口 cwnd, 接收窗口 rwnd)

**四种算法**：

| 算法 | 机制 |
|---|---|
| 慢开始 | cwnd 从较小值开始，每经过一个传输轮次翻倍（指数增长），直到达到门限 ssthresh |
| 拥塞避免 | 每经过一个传输轮次 cwnd 加 1（线性增长） |
| 快重传 | 收到 3 个重复确认时立即重传，不必等超时 |
| 快恢复 | 收到 3 个重复确认时把 ssthresh 与 cwnd 都设为原 cwnd 的一半，随后执行拥塞避免 |

**门限 ssthresh**：用于界定慢开始与拥塞避免——cwnd < ssthresh 执行慢开始，cwnd ≥ ssthresh 执行拥塞避免。

**状态转换**：

| 事件 | 处理 |
|---|---|
| 超时 | ssthresh = cwnd / 2，cwnd = 1，重新慢开始 |
| 3 个重复确认 | ssthresh = cwnd / 2，cwnd = ssthresh（快恢复），进入拥塞避免 |

**快恢复的取值依据**：收到重复确认说明接收方仍在收到报文段，只是中间某个报文段丢失，网络并未严重拥塞，故 cwnd 降到 ssthresh 而非降到 1。

**思想**：TCP 拥塞控制具有**加法增大、乘法减小（AIMD）**的特点——增长时线性试探，出现拥塞时成倍退回，在效率与稳定之间取得平衡。

## 流量控制的零窗口与持续计时器

> section_id: basic-cn-transport-flow-zero-window
> kp_ids: [cn.transport.tcp_flow]
> primary_kp: cn.transport.tcp_flow

**接收窗口 rwnd**：接收方通过确认报文中的窗口字段告知自己当前的接收缓存余量，发送方据此调整发送窗口，防止压垮接收方。

**零窗口与死锁**：当接收方缓存满时通告窗口为 0，发送方停止发送；之后若接收方缓存腾空并发出新的窗口通知，而该通知丢失，则双方会互相等待，形成死锁。

**持续计时器**：只要收到对方的零窗口通知，就启动持续计时器。超时后发送一个**零窗口探测报文**（仅携带一个字节）；对方在确认该探测报文时给出当前接收窗口值——若仍为 0 则重启计时器，若不为 0 则死锁被打破。探测报文本身也有重传计时器，丢失后可重传。

**思想**：流量控制是**收端问题**，通过「通告窗口 + 探测」闭环，解决「窗口通知丢失」导致的僵局。

## 可靠传输的实现机制

> section_id: basic-cn-transport-reliable
> kp_ids: [cn.transport.tcp]
> primary_kp: cn.transport.tcp

**定义**：TCP 面向字节流，每个字节都有一个序号，收发双方以字节为单位确认与滑动。

**共同保证可靠传输的机制**：

- **序号与确认**：接收方只对按序收到的最高序号给出确认
- **超时重传**：发送方启动计时器，超时未收到确认则重传
- **快重传**：收到 3 个重复确认立即重传，不等超时
- **滑动窗口**：发送窗口限制「已发未确认」的数据量
- **校验和**：检测传输中的比特差错
- **流量控制**：防止发送过快导致接收方缓存溢出

**思想**：TCP 的可靠不是靠单点，而是若干机制协同——序号给出「顺序」，确认与重传给出「不丢」，窗口给出「不压垮」。
