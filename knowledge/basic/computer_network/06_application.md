## DNS

> section_id: basic-cn-application-dns
> kp_ids: [cn.application.dns]
> primary_kp: cn.application.dns

**定义**：域名与 IP 地址之间的分布式目录服务。

**为什么**：人用名字、机器用地址；需要可扩展的层次命名与缓存。

**思想**：**分层命名 + 分布式授权**；缓存降低查询延迟与根服务器压力。

## 网络应用模型：C/S 与 P2P

> section_id: basic-cn-application-models
> kp_ids: [cn.application]
> primary_kp: cn.application

**客户-服务器（C/S）方式**：客户是服务请求方，服务器是服务提供方。服务器长期运行、被动等待请求，可同时服务多个客户，需较强的硬件支持。

**对等（P2P）方式**：不区分固定的客户与服务器，每个对等方既可请求也可提供，节点越多资源越丰富，可扩展性好。

**对比**：

| 特性 | C/S 方式 | P2P 方式 |
|---|---|---|
| 中心服务器 | 需要 | 不需要 |
| 可扩展性 | 受服务器限制 | 好 |
| 管理难度 | 较易 | 较难 |
| 安全性 | 较高 | 较低 |

**思想**：C/S 把服务集中、便于管理，P2P 把服务分散、利于扩展；两者是应用层组织通信的基本形态。

## 域名结构与域名服务器

> section_id: basic-cn-application-dns-structure
> kp_ids: [cn.application.dns]
> primary_kp: cn.application.dns

**域名结构**：因特网采用**层次树状结构**命名，域名由标号序列组成，各标号之间用点隔开，形式为「…三级域名.二级域名.顶级域名」。

**顶级域名**分三类：

- **国家/地区顶级域名**：如 .cn、.us、.jp
- **通用顶级域名**：如 .com、.net、.org、.edu、.gov
- **基础结构域名**：如 .arpa

**域名服务器**（分布式部署）：

| 类型 | 职责 |
|---|---|
| 根域名服务器 | 知道所有顶级域名服务器的地址 |
| 顶级域名服务器 | 管理在该顶级域名下注册的二级域名 |
| 权限域名服务器 | 管理一个区的域名 |
| 本地域名服务器 | 主机默认使用的域名服务器 |

**思想**：**分层命名 + 分布式授权**——一个服务器只负责自己管辖的那部分域名，从而避免单点、便于扩展；域名只是逻辑概念，不反映物理位置。

## 域名解析：递归查询与迭代查询

> section_id: basic-cn-application-dns-resolution
> kp_ids: [cn.application.dns]
> primary_kp: cn.application.dns

**递归查询**：主机向本地域名服务器的查询通常采用递归查询——若本地域名服务器不知道答案，就代替主机继续向其他域名服务器查询，直到得到结果并返回。

**迭代查询**：本地域名服务器向根域名服务器的查询通常采用迭代查询——被查询的服务器要么给出结果，要么告诉下一步应向哪个域名服务器查询。

**解析流程**：主机 →（递归）本地域名服务器 →（迭代）根域名服务器 →（迭代）顶级域名服务器 →（迭代）权限域名服务器 → 返回最终 IP 地址。

**高速缓存**：域名服务器维护高速缓存，存放最近查询过的域名与地址映射，并设置生存时间；主机也有缓存。缓存可显著减少查询时延与根服务器压力。

**思想**：递归把「帮我查到」的责任交给下层服务器，迭代只给出「下一步该问谁」；二者配合使查询在层次结构中逐级推进。

## DHCP 动态主机配置

> section_id: basic-cn-application-dhcp
> kp_ids: []

**定义**：DHCP（动态主机配置协议）提供**即插即用连网**机制，使主机加入新网络时自动获取 IP 地址等配置，而无需手工设置。DHCP 基于 UDP 工作，服务器端口 67、客户端端口 68。

**四步交互**：

| 步骤 | 报文 | 源地址 | 目的地址 |
|---|---|---|---|
| 1 | DHCP 发现 | 0.0.0.0 | 255.255.255.255 |
| 2 | DHCP 提供 | 服务器 IP | 255.255.255.255 |
| 3 | DHCP 请求 | 0.0.0.0 | 255.255.255.255 |
| 4 | DHCP 确认 | 服务器 IP | 255.255.255.255 |

服务器在提供报文中给出 IP 地址、子网掩码、地址租期、默认网关与 DNS 服务器等信息。

**租约更新**：租用期过半时，客户端请求更新租约；服务器同意则发回确认，不同意则发回否认，客户端须重新申请。

**中继代理**：不需要每个网络都配 DHCP 服务器——中继代理收到客户端广播的发现报文后，以单播方式转发给其他网络的 DHCP 服务器。

**思想**：DHCP 把地址分配从「人工静态配置」变为「服务器集中管理 + 租约」，适应主机频繁加入/离开的网络。

## FTP 的双连接与工作模式

> section_id: basic-cn-application-ftp-modes
> kp_ids: [cn.application.ftp]
> primary_kp: cn.application.ftp

**定义**：FTP（文件传送协议）是使用最广泛的文件传送协议，提供交互式访问，允许指明文件类型与格式、设置存取权限，使用 TCP 提供可靠传输。

**双连接**：

- **控制连接**：端口 21，在整个会话期间保持打开，用于传送控制命令
- **数据连接**：用于传送文件，每次传输时建立、传输完毕后关闭

两个连接分离，故 FTP 属于**带外控制**——控制信息与数据走不同连接。

**工作模式**：

- **主动模式**：服务器从端口 20 主动连接客户端指定的端口
- **被动模式**：服务器打开一个随机端口并告知客户端，由客户端主动连接

**思想**：控制面与数据面分离，使命令交互与批量数据传输互不干扰。

## 电子邮件协议：SMTP、MIME、POP3、IMAP

> section_id: basic-cn-application-email-protocols
> kp_ids: [cn.application.email]
> primary_kp: cn.application.email

**三个组成部分**：用户代理（读写邮件的软件）、邮件服务器（发送、接收并维护用户邮箱）、协议（发送协议与读取协议）。

**发送流程**：发件人用户代理 →（SMTP）发件方邮件服务器 →（SMTP）收件方邮件服务器 →（POP3/IMAP）收件人用户代理。

**SMTP（发送）**：使用 TCP，端口 25；分连接建立、邮件传送、连接释放三个阶段。只能传送 7 位 ASCII 文本，不能传送非英文文本与二进制文件。

**MIME**：在 SMTP 基础上扩展，允许传送非 ASCII 内容（图片、音频、视频等），通过首部说明数据类型与编码方式。

**POP3（接收）**：使用 TCP，端口 110；有「下载并保留」「下载并删除」等方式，功能简单，不支持在服务器上管理邮件。

**IMAP（接收）**：使用 TCP，端口 143；可在服务器上管理邮件（建文件夹、搜索），支持只下载首部、需要时再取正文，比 POP3 灵活。

**思想**：电子邮件是**存储转发**的异步消息系统，发送与读取使用不同协议，与会话式请求响应不同。

## 万维网与 HTTP 报文

> section_id: basic-cn-application-www
> kp_ids: [cn.application.http]
> primary_kp: cn.application.http

**三个重要概念**：

- **URL**：统一资源定位符，格式为 `协议://主机:端口/路径?查询#片段`
- **HTML**：超文本标记语言，描述万维网页面的标准语言
- **HTTP**：超文本传送协议，工作于应用层，使用 TCP 可靠传送

**HTTP 工作过程**：服务器监听端口 80 → 建立 TCP 连接 → 浏览器发出请求 → 服务器返回响应 → 释放连接。

**请求与响应报文**：请求报文首行为「方法 URL 版本」，响应报文首行为「版本 状态码 短语」，之后是若干首部字段、空行与实体主体。

**常用请求方法**：

| 方法 | 说明 | 幂等 |
|---|---|---|
| GET | 获取资源 | 是 |
| POST | 提交数据 | 否 |
| PUT | 替换资源 | 是 |
| DELETE | 删除资源 | 是 |
| HEAD | 获取首部 | 是 |

**状态码类别**：

| 类别 | 含义 | 示例 |
|---|---|---|
| 1xx | 信息类 | 100 |
| 2xx | 成功 | 200 |
| 3xx | 重定向 | 301、302 |
| 4xx | 客户端错误 | 404、403 |
| 5xx | 服务器错误 | 500 |

**思想**：HTTP 是无状态请求/响应协议，方法、状态码构成语义接口，状态维护靠 Cookie 等机制补足。

## HTTP 版本演进与缓存机制

> section_id: basic-cn-application-http-versions
> kp_ids: [cn.application.http]
> primary_kp: cn.application.http

**连接方式**：HTTP/1.0 为非持续连接（每个对象单独建立 TCP 连接）；HTTP/1.1 为持续连接，一个 TCP 连接可传送多个对象，并可流水线式连续发送请求。

**Cookie**：HTTP 无状态，服务器可在响应中通过首部发送 Cookie，浏览器保存后，之后对同一服务器的请求自动附带 Cookie，从而在服务器端记录用户状态。

**万维网缓存与代理服务器**：代理服务器（Web 缓存）代替浏览器与服务器通信，缓存近期访问过的资源，减少时延与通信量。缓存验证机制：未过期则直接返回副本；已过期则向原始服务器发条件请求，文档未修改返回 304（不含实体主体），已修改返回 200 与新文档。

**版本演进**：

- **HTTP/1.1**：文本格式、持续连接，存在队头阻塞
- **HTTP/2**：二进制分帧、多路复用（一个连接并行多个流）、头部压缩、服务器推送，缓解应用层队头阻塞
- **HTTP/3**：基于 QUIC（运行在 UDP 上），各流独立传输，彻底解决传输层队头阻塞，支持 0-RTT 会话恢复与连接迁移

**思想**：HTTP 的演进围绕「减少连接开销、利用并行、降低队头阻塞」；加密与传输优化（HTTPS、QUIC）逐步内建进协议栈。
